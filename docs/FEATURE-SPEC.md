# 기능 명세서 (v0.1, legacy)

> **구현 기준 아님:** 2026-09-20 이후 MVP는 [docs/mvp/README.md](mvp/README.md)와 [확정 결정](mvp/decisions.md)을 따른다. 이 문서는 데모 분석 이력 보존용이다.

> API/DB 세부 구현은 [API-DESIGN-DRAFT.md](API-DESIGN-DRAFT.md) 참고.
> 이 문서는 "무엇을 하는 기능인지 · 어떤 규칙으로 동작하는지 · 어떤 예외를 처리하는지"에 집중한다.
> 각 기능은 MVP 포함 여부를 표시 — 없으면 MVP 범위.

## v1 구현 범위 (지금 착수하는 플로우)

> **2026-09-17 팀 논의로 플로우 변경(PR #1, lbeul372 의견 채택)**: 애초 "로그인은 선택 시점(저장할 때만)"이던
> 게스트-우선 설계를 **로그인-우선**으로 바꾼다. 비로그인 상태로 코스 생성까지 체험하게 하면 기존 회원이
> 비회원처럼 코스를 만들 때 자신의 기존 여행과 날짜가 겹치는지 사전에 확인하기 어렵고, 새 온보딩 결과와
> 기존 취향 중 무엇을 적용할지도 별도 정책이 필요해진다 — 로그인 후 기존 일정·취향을 기준으로 만들면 이 과정이 단순해진다.

```
초대장(서비스 진입, 있는 경우 — §6) 또는 직접 방문
        │
        ▼
1. 로그인 / 회원가입 (§1) — 필수, 맨 앞 단계
        │
        ▼
2. 온보딩 — 최초 설문 미완료 시에만 진행 (§2)
   (이미 완료했다면 건너뛰고 저장된 취향을 그대로 사용)
        │
        ▼
3. 캘린더 — 여행 시작·종료일 선택 (§5.2)
   기존 CONFIRMED 여행과 날짜가 겹치면 선택 불가
   (겹치는 기간을 쓰려면 기존 여행을 먼저 삭제해야 함)
        │
        ▼
4. 지역 추첨 — 슬롯머신 (§3)
        │
        ▼
5. 코스 슬롯 생성 + 잠금/리롤/개수조정 (§4)
        │
        ▼
6. 코스 확정 저장 (§5.1)
```

- **게스트(비로그인) 사용 경로는 v1에서 없앤다.** 온보딩·지역추첨·코스생성 API는 모두 "인증 선택(Optional Auth)"이
  아니라 **인증 필수**로 바뀐다 — API-DESIGN-DRAFT.md의 `tasteVector` 게스트 파라미터·Optional Auth 분기는 제거
  대상이다(§API-DESIGN-DRAFT 갱신 참고).
- **개인 일정 규칙**: 최초 온보딩 결과는 계속 유지하고, 사용자가 직접 "취향 재검사"를 요청할 때만 갱신한다(§2).
  여행 생성 시 시작·종료일이 기존에 확정된 다른 여행과 겹치면 생성 자체를 막는다(§5.2). 확정 후에는 여행
  시작·종료일은 변경할 수 없지만, 기간 내 날짜별 장소와 방문 순서는 계속 수정할 수 있다(§4.3/§5.1).
- **친구와 함께하는 일정 규칙**(§6, v1 범위 밖이지만 설계는 지금 반영): 최초 코스는 생성자(OWNER)의 취향
  기준으로 만들어진다. 참여자를 초대하면 알림이 가고, 참여자의 기존 여행과 날짜가 겹치면 수락할 수 없다.
  수락하면 같은 여행이 참여자 캘린더에도 그대로 표시된다 — 별도 복사본을 만들지 않는다. 생성자와 참여자는
  세부 코스 수정·친구 초대·일정 탈퇴에 대해 동등한 권한을 가진다.

**v1에서 제외(후속/v2)**: §6 친구 초대·같이 보기 전체, §5.2의 구글 캘린더 실연동(자체 캘린더 날짜 지정·중복
차단은 위 변경으로 v1에 포함된다). 아래 섹션 번호는 문서 전체 구조 유지를 위해 그대로 두되, 지금 구현 순서는
위 6단계다.

## 목차
1. 회원가입 / 로그인 (이메일 + 소셜)
2. 온보딩 (취향 입력)
3. 지역 추첨
4. 코스 생성 (슬롯 잠금 · 리롤 · 개수 조정)
5. 코스 확정 · 캘린더 연동
6. 친구 초대 · 같이 보기
7. 추천 시스템 (관광지 임베딩 배치 · 콘텐츠 기반 매칭)
8. 관리자 — 임베딩 배치 운영

## 1. 회원가입 / 로그인

### 1.1 이메일 회원가입
| 항목 | 내용 |
|---|---|
| 설명 | 이메일+비밀번호로 신규 계정 생성 |
| 입력 | email, password, nickname |
| 비즈니스 규칙 | email 형식 검증·중복 불가 · password 8자 이상 · nickname 1~30자 · password는 BCrypt 해시로만 저장 |
| 예외 | 이메일 중복 → 409 · 형식 오류 → 400 (필드별 에러 메시지) |
| 완료 후 동작 | 즉시 로그인 처리(JWT 발급). 로그인/회원가입은 v1 플로우의 맨 앞 단계다(§v1 구현 범위, 2026-09-17 팀 논의로 변경 — 이전엔 "코스 생성까지 게스트로 체험 후 저장 시점에 가입"이었으나 폐지) |

### 1.2 이메일 로그인
| 항목 | 내용 |
|---|---|
| 입력 | email, password |
| 비즈니스 규칙 | 이메일 없음/비밀번호 불일치를 **같은 에러 메시지**로 응답(계정 존재 여부 노출 방지 — 데모 `AppUserDetailsService` 관례 계승) |
| 예외 | 인증 실패 → 401(동일 메시지) |

### 1.3 소셜 로그인 (카카오 / 구글)
| 항목 | 내용 |
|---|---|
| 설명 | 프론트가 OAuth 인가코드를 받아 백엔드로 전달, 백엔드가 토큰 교환·프로필 조회 후 자체 JWT 발급 |
| 입력 | provider, code |
| 비즈니스 규칙 | provider+providerUserId로 기존 계정 조회 → 있으면 로그인, 없으면 신규 User+SocialAccount 생성(비밀번호 없이) · 같은 이메일의 기존 이메일 계정이 있어도 **자동 병합하지 않음**(계정 탈취 방지 — 사용자가 명시적으로 연결해야 함, §1.4) |
| 예외 | provider 토큰 교환 실패 → 502 · 이메일/닉네임 등 프로필 조회 실패 → 임시 닉네임(예: "여행자1234")로 대체 후 가입 |

### 1.4 계정 연결 (기존 계정에 소셜 추가)
| 항목 | 내용 |
|---|---|
| 설명 | 로그인된 상태에서 소셜 계정을 추가 연결(카카오+구글 동시 가능) |
| 비즈니스 규칙 | 이미 다른 유저에 연결된 provider+providerUserId는 연결 불가(409) |
| MVP 포함 | 아니오 — 후속 |

### 1.5 로그아웃 / 토큰 갱신
| 항목 | 내용 |
|---|---|
| 로그아웃 | 전달받은 refresh 토큰을 revoked=true 처리 |
| 갱신 | refresh 토큰 유효성 확인(해시 대조, 만료·revoked 체크) → 새 access 토큰 발급. **refresh 토큰 자체는 재사용 시 회전(rotate)** — 탈취 시 재사용 탐지 여지를 남김 |
| 예외 | 만료/폐기된 refresh 토큰 → 401, 재로그인 유도 |

## 2. 온보딩 (취향 입력)

| 항목 | 내용 |
|---|---|
| 설명 | **로그인 필수**(2026-09-17 팀 논의로 변경 — 게스트 온보딩 폐지). 최초 1회 진행하며, 이미 완료한 사용자는 §v1 플로우에서 이 단계를 건너뛴다. 자연 선호도·여행 스타일(MBTI류)·선호 태그 등을 질문으로 수집 |
| 입력 | 질문별 응답(단일선택/다중선택/자유서술 혼재) |
| 처리 | 응답 전체를 `onboarding_responses`에 원본 저장 → 프로필 텍스트로 합성(§3.1 텍스트 합성 규칙과 동일한 자연어 문장형 스타일) → Ollama 임베딩 → `user_taste_vectors` 저장. 이후 요청은 서버가 user_id로 벡터를 찾아 씀 |
| 비즈니스 규칙 | **모든 질문에 답하지 않아도 진행 가능** — 미답변 항목은 중립으로 처리(데모 PRD 원칙: "많이 고른 사람이 안 고른 사람보다 과대표되지 않는다" 계승) · **최초 결과는 계속 유지하며, 사용자가 명시적으로 "취향 재검사"를 요청할 때만 갱신**한다(팀 논의로 확정) — 재응답 시 새 응답이 기존 것을 덮어씀(히스토리는 `onboarding_responses`에 누적 보관, 최신 것만 현재 벡터에 반영, §7.3) |
| 예외 | 완전 미응답으로 제출 → 저장은 허용하되 `user_taste_vectors` 생성은 보류(추천 시 §7의 "취향 없음" 폴백 적용) |

## 3. 지역 추첨

| 항목 | 내용 |
|---|---|
| 설명 | [추천] 버튼 → 도 → 시/군 2단계로 지역을 뽑는 "슬롯머신" 연출용 결과 반환 |
| 입력 | mode(`FULL_RANDOM` \| `PREFERENCE_WEIGHTED`), situation(선택) |
| 비즈니스 규칙 | `FULL_RANDOM`: 250개 시군구 균등 확률. `PREFERENCE_WEIGHTED`: 지역별 취향 적합도(그 지역 관광지들과 사용자 벡터의 평균 유사도)를 가중치로 한 **확률적** 추첨(최고 적합 지역이 매번 나오지는 않음 — 발견의 재미 유지) · **관광지가 없거나 준비도가 낮은 지역(최소 관광지 수 미달)은 추첨 후보에서 제외**(데모 `MIN_ATTRACTIONS` 게이트와 동일 원칙) |
| 기본 모드 | 사용자가 프로필에 기본 모드(`FULL_RANDOM`/`PREFERENCE_WEIGHTED`)를 저장해두면 추첨 화면은 그 값을 기본 선택 상태로 보여주고, 화면의 체크박스로 그 자리에서 바로 바꿀 수 있게 한다(팀 논의로 확정, §9) — 매번 처음부터 고르는 부담은 없애되 그때그때 바꿀 여지는 남긴다 |
| 예외 | 사용자 취향 벡터가 없는데 `PREFERENCE_WEIGHTED` 요청 → `FULL_RANDOM`으로 자동 폴백(에러 대신 우아한 대체) |
| 재시도 | 결과가 마음에 안 들면 다시 호출 가능(횟수 제한 없음 — MVP) |

## 4. 코스 생성 (슬롯 잠금 · 리롤 · 개수 조정)

### 4.1 코스 초안 생성
| 항목 | 내용 |
|---|---|
| 설명 | 추첨된 지역 기준으로 관광지 슬롯 N개를 채운 코스 초안 생성 |
| 입력 | regionId, transport, origin(출발지 좌표/주소), situation, stopCount(기본값 예: 4) |
| 비즈니스 규칙 | 관광지 후보는 `embedding_status='DONE'`인 것만(§7) · 유사도 상위권에서 **가중 랜덤 추출**(항상 top-N 고정이면 같은 지역에서 매번 같은 코스만 나옴 — 다양성 확보) · 슬롯 순서(order_index)는 출발지 기준 동선 정렬 — **카카오모빌리티 자동차 길찾기 API로 계산**(팀 논의로 확정, §9. 저장 시점 1회 계산 원칙은 그대로 유지) |
| 예외 | 지역 내 준비된(embedding DONE) 관광지가 stopCount보다 적음 → 있는 만큼만 채우고 응답에 `actualStopCount` 명시 |

### 4.2 슬롯 잠금 / 리롤
| 항목 | 내용 |
|---|---|
| 설명 | 마음에 드는 슬롯은 잠금(유지), 나머지만 다시 뽑기 — 반복 가능 |
| 입력 | 현재 슬롯 전체(각 슬롯의 attractionId + locked 여부) |
| 비즈니스 규칙 | `locked=true` 슬롯은 그대로 응답에 재포함 · `locked=false` 슬롯만 새로 추천 · **이번 요청에 담긴 모든 attractionId(잠긴 것 포함)는 리롤 후보에서 제외**(직전에 본 걸 또 보여주지 않음) · 전부 잠그면(리롤 대상 0개) 그대로 반환 |
| 예외 | 리롤할 후보가 지역 내에 더 없음(다 소진) → 빈 슬롯 유지 + `exhausted: true` 플래그로 UI에 "더 이상 후보 없음" 표시 유도 |
| 저장 여부 | 이 단계는 서버에 영속화하지 않음(stateless, §5.3) — 새로고침하면 초안 소실, 확정 전까지는 가벼운 상태로 취급 |

### 4.3 개수 조정 / 수동 추가·삭제
| 항목 | 내용 |
|---|---|
| 설명 | 슬롯 개수를 늘리거나 줄이기, 특정 관광지를 검색해서 수동으로 끼워넣기/빼기 |
| 비즈니스 규칙 | 개수를 늘리면 늘어난 만큼 새 슬롯이 추천으로 채워짐(잠금 슬롯 영향 없음) · 수동 추가된 슬롯은 `source=MANUAL`로 표시(추천 슬롯과 구분, §6 DB) |
| MVP 포함 | 개수 조정은 포함, 검색 기반 수동 추가는 후속(관광지 검색 API가 별도 필요) |

## 5. 코스 확정 · 캘린더 연동

### 5.1 코스 확정
| 항목 | 내용 |
|---|---|
| 설명 | 슬롯 초안을 실제로 저장 — 이 시점부터 `trip_plans`/`trip_stops`로 영속화. 로그인은 이미 v1 플로우 맨 앞에서 끝난 상태이므로(§v1 구현 범위), 이 단계에서 새삼 로그인을 요구하는 분기는 없다 |
| 비즈니스 규칙 | 확정 시점에 동선(순서)을 재계산해 고정(카카오모빌리티 자동차 길찾기 API를 쓴다면 **이 1회만** 호출, §9) · 확정 후에는 여행 시작·종료일 변경과 슬롯 잠금/리롤(추첨 재시도)은 안 되지만, **날짜별 장소 순서 변경·삭제는 v1에 포함**한다(팀 논의로 확정 — 개인 일정 요구사항상 필수라 기존 "후속" 계획에서 앞당김) |

### 5.2 캘린더 — 여행 시작·종료일 지정
| 항목 | 내용 |
|---|---|
| 설명 | v1에서는 **지역 추첨·코스 생성보다 먼저** 진행하는 필수 단계다(2026-09-17 팀 논의로 순서 변경) — 로그인 직후(또는 최초 온보딩 직후) 시작·종료일부터 정하고 나서 지역 추첨·코스 생성으로 넘어간다 |
| 비즈니스 규칙 | 같은 사용자의 기존 `CONFIRMED` 여행과 날짜가 하루라도 겹치면 **선택 자체를 차단**한다(겹치는 기간을 쓰려면 기존 여행을 먼저 삭제해야 함) — "경고만 하고 차단은 안 함"이던 초기 안(구버전 §9)을 팀 논의로 강화했다. 단 이건 **자체 캘린더**(우리 서비스 안의 다른 여행)에만 적용되는 규칙이고, 구글 캘린더 등 **외부** 캘린더 연동은 별개 후속 기능으로 거기서는 여전히 경고만 하고 차단하지 않는다(외부 일정까지 서버가 강제할 근거가 약함) |
| 생성 후 | 확정된 시작·종료일은 변경 불가 — 다른 기간을 쓰려면 새 여행을 만들어야 함. 날짜별 장소·순서 변경은 §5.1 참고 |
| MVP 포함 | 자체 캘린더(위 규칙)는 v1 포함. 구글 캘린더 실연동은 후속(v2) |

## 6. 친구 초대 · 같이 보기

| 항목 | 내용 |
|---|---|
| 설명 | 확정된(또는 확정 전) 코스를 링크로 공유해서 친구를 초대, 같이 보기 |
| 입력 | tripPlanId → 초대 링크 발급(토큰 기반, 만료시간 있음) |
| 비즈니스 규칙 | 초대 링크는 **비회원도 열 수 있다**(2026-09-17 팀 논의로 확정, Suuunz 의견) — when2meet처럼 비회원이 링크로 들어와도 그 링크를 통해 여행 계획 페이지에 계속 접근·열람할 수 있다. 단 실제로 "참여자"로 등록되어(`trip_members` row 생성) 코스 수정·초대·탈퇴 권한을 가지려면 로그인/회원가입이 필요하다 — **열람과 참여를 구분**한다 · 초대자(OWNER)만 초대 링크 재발급/무효화 가능 · 링크 만료 후 접근 시 "만료됨" 안내, 재발급 요청 유도 · **참여자의 기존 CONFIRMED 여행과 날짜가 겹치면 수락 불가**(개인 일정의 날짜 중복 차단과 동일 원칙, §5.2) · 수락 시 별도 복사본을 만들지 않고 같은 `trip_plans` row를 참여자 캘린더에도 그대로 노출 · 생성자(OWNER)와 참여자(MEMBER)는 세부 코스 수정·추가 초대·일정 탈퇴에 대해 **동등한 권한**을 가진다 — OWNER/MEMBER 구분은 권한 차등이 아니라 "누가 만들었는가" 기록용으로만 쓴다 |
| 친구 목록(선택 기능) | 별도로 "친구 추가"(상호 수락) 기능도 제공 — 초대 링크와 별개로 자주 같이 가는 사람을 목록화 |
| MVP 포함 | **아니오 — §6 전체가 v1 범위 밖(후속/v2)이다.** 문서 상단 "v1 구현 범위"에서 확정한 것과 일치시킴(이전 버전에선 "초대 링크는 포함"이라고 써서 불일치가 있었음 — Copilot 리뷰로 발견, 여기서 정정). 위 비즈니스 규칙은 v2 착수 시 바로 적용할 설계로 팀 논의 결과를 미리 반영해둔 것이고, 실제 구현 우선순위는 v2 착수 시 다시 정한다 |

## 9. 팀 논의로 결정된 정책 (2026-09-17, PR #1 코멘트 반영)

과거엔 아래 4가지가 "안(案)"으로만 표시된 미확정 정책이었다. lbeul372·Suuunz의 리뷰 코멘트로 다음과 같이 확정했다:
1. **캘린더 중복 정책** — 자체 캘린더(우리 서비스 내 다른 여행)는 겹치면 **차단**. 외부(구글) 캘린더 연동은 후속 기능이며 거기서는 **경고만**(§5.2)
2. **완전랜덤/취향반영랜덤 기본값** — 프로필에 기본값을 저장해두고, 추첨 화면에서 체크박스로 바로 바꿀 수 있게 함(§3)
3. **동선 계산 정밀도** — 카카오모빌리티 **자동차 길찾기 API** 채택(§API-DESIGN-DRAFT §3 참고). self-serve로 즉시 발급 가능, 일 10,000건 무료·초과 시 건당 8원(100만 건까지)이라 MVP 트래픽 규모에서 사실상 무료. 단, **도보 길찾기 API는 별도 제휴 심사가 필요**해 승인 여부·소요기간이 불확실 — 관광지 간 도보 이동 구간은 MVP에서는 자동차 API 결과 또는 단순 거리 근사로 대체하고, 도보 API 제휴가 승인되면 교체한다
4. **친구 초대 링크의 비회원 접근** — 열람(링크로 계속 접근)은 비회원도 허용, 실제 참여(코스 수정 권한)는 로그인 필요(§6)
