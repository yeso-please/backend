# 기능 명세서 (v0.1)

> API/DB 세부 구현은 [API-DESIGN-DRAFT.md](API-DESIGN-DRAFT.md) 참고.
> 이 문서는 "무엇을 하는 기능인지 · 어떤 규칙으로 동작하는지 · 어떤 예외를 처리하는지"에 집중한다.
> 각 기능은 MVP 포함 여부를 표시 — 없으면 MVP 범위.

## v1 구현 범위 (지금 착수하는 플로우)

**로그인은 맨 앞이 아니라 선택 시점이다.** 비로그인 상태로 온보딩~코스 생성까지 전부 체험 가능하고,
로그인은 "이 코스를 서버에 저장하고 싶을 때"만 필요하다.

```
                    2. 온보딩 — 취향 입력 (§2)
                            │
                            ▼
                    3. 지역 추첨 — 슬롯머신 (§3)
                            │
                            ▼
                    4. 코스 슬롯 생성 + 잠금/리롤/개수조정 (§4)
                            │
                ┌───────────┴────────────┐
                ▼                         ▼
        비로그인 상태로 종료          [저장하기] 버튼
        → 클라이언트가 결과를          → 로그인 안 돼 있으면 이 시점에
          localStorage 에만 보관         1. 로그인/회원가입 유도(§1)
          (서버엔 아무 것도 안 남음)      2. 로그인 성공 후 들고 있던
                                            코스를 그대로 서버 확정 API로
                                            전송 → 5. 코스 확정 저장(§5.1)
```

- **비로그인(게스트) 사용자**: 온보딩 응답을 서버에 보내면 임베딩만 계산해서 벡터를 그대로 클라이언트에 돌려주고,
  서버 DB에는 아무것도 저장하지 않는다(§2 게스트 동작 참고). 이후 지역 추첨·코스 생성 요청에는 이 벡터를
  클라이언트가 매번 실어 보낸다 — 로그인 사용자가 서버에 저장된 취향을 자동으로 쓰는 것과 대비되는 지점.
- **로그인 사용자**: 온보딩 응답이 `onboarding_responses`/`user_taste_vectors`에 저장되고, 이후 요청은 벡터를
  안 보내도 서버가 알아서 찾아 씀.
- **게스트 → 로그인 전환**: 새 엔드포인트를 따로 만들지 않는다 — 게스트가 만든 코스 슬롯(client가 들고 있는
  상태)을 로그인 직후 그대로 `POST /api/courses`(§5.1, 인증 필요)에 실어 보내면 그게 곧 "저장"이 된다.
  데모의 `VisitOnboardingController`가 세션 취향을 로그인 시 DB로 이관하던 것과 같은 아이디어를
  세션 대신 클라이언트 상태로 구현한 셈(§DEMO-REFERENCE.md 참고).

**v1에서 제외(후속/v2)**: §5.2 캘린더 연동, §6 친구 초대·같이 보기. 아래 섹션 번호는 문서 전체 구조 유지를 위해 그대로 두되,
지금 구현 순서는 이 5단계만 대상으로 한다.

## 목차
1. 회원가입 / 로그인 (이메일 + 소셜)
2. 온보딩 (취향 입력)
3. 지역 추첨
4. 코스 생성 (슬롯 잠금 · 리롤 · 개수 조정)
5. 코스 확정 · 캘린더 연동
6. 친구 초대 · 같이 보기
7. 추천 시스템 (관광지 임베딩 배치 · 콘텐츠 기반 매칭)
8. 관리자 — 임베딩 배치 운영

## 1. 회원가입 / 로그인

### 1.1 이메일 회원가입
| 항목 | 내용 |
|---|---|
| 설명 | 이메일+비밀번호로 신규 계정 생성 |
| 입력 | email, password, nickname |
| 비즈니스 규칙 | email 형식 검증·중복 불가 · password 8자 이상 · nickname 1~30자 · password는 BCrypt 해시로만 저장 |
| 예외 | 이메일 중복 → 409 · 형식 오류 → 400 (필드별 에러 메시지) |
| 완료 후 동작 | 즉시 로그인 처리(JWT 발급). **가입 시점은 유동적** — 처음부터 가입할 수도 있고, 게스트로 온보딩~코스 생성까지 다 해본 뒤 [저장하기]에서 가입할 수도 있음(v1 구현 범위 참고). 후자의 경우 가입 직후 클라이언트가 들고 있던 코스를 곧바로 §5.1 확정 API로 전송 |

### 1.2 이메일 로그인
| 항목 | 내용 |
|---|---|
| 입력 | email, password |
| 비즈니스 규칙 | 이메일 없음/비밀번호 불일치를 **같은 에러 메시지**로 응답(계정 존재 여부 노출 방지 — 데모 `AppUserDetailsService` 관례 계승) |
| 예외 | 인증 실패 → 401(동일 메시지) |

### 1.3 소셜 로그인 (카카오 / 구글)
| 항목 | 내용 |
|---|---|
| 설명 | 프론트가 OAuth 인가코드를 받아 백엔드로 전달, 백엔드가 토큰 교환·프로필 조회 후 자체 JWT 발급 |
| 입력 | provider, code |
| 비즈니스 규칙 | provider+providerUserId로 기존 계정 조회 → 있으면 로그인, 없으면 신규 User+SocialAccount 생성(비밀번호 없이) · 같은 이메일의 기존 이메일 계정이 있어도 **자동 병합하지 않음**(계정 탈취 방지 — 사용자가 명시적으로 연결해야 함, §1.4) |
| 예외 | provider 토큰 교환 실패 → 502 · 이메일/닉네임 등 프로필 조회 실패 → 임시 닉네임(예: "여행자1234")로 대체 후 가입 |

### 1.4 계정 연결 (기존 계정에 소셜 추가)
| 항목 | 내용 |
|---|---|
| 설명 | 로그인된 상태에서 소셜 계정을 추가 연결(카카오+구글 동시 가능) |
| 비즈니스 규칙 | 이미 다른 유저에 연결된 provider+providerUserId는 연결 불가(409) |
| MVP 포함 | 아니오 — 후속 |

### 1.5 로그아웃 / 토큰 갱신
| 항목 | 내용 |
|---|---|
| 로그아웃 | 전달받은 refresh 토큰을 revoked=true 처리 |
| 갱신 | refresh 토큰 유효성 확인(해시 대조, 만료·revoked 체크) → 새 access 토큰 발급. **refresh 토큰 자체는 재사용 시 회전(rotate)** — 탈취 시 재사용 탐지 여지를 남김 |
| 예외 | 만료/폐기된 refresh 토큰 → 401, 재로그인 유도 |

## 2. 온보딩 (취향 입력)

| 항목 | 내용 |
|---|---|
| 설명 | 로그인 여부와 무관하게 진행 가능(v1 구현 범위 — 비로그인 체험). 자연 선호도·여행 스타일(MBTI류)·선호 태그 등을 질문으로 수집 |
| 입력 | 질문별 응답(단일선택/다중선택/자유서술 혼재) |
| 처리 — 로그인 사용자 | 응답 전체를 `onboarding_responses`에 원본 저장 → 프로필 텍스트로 합성(§3.1 텍스트 합성 규칙과 동일한 자연어 문장형 스타일) → Ollama 임베딩 → `user_taste_vectors` 저장. 이후 요청은 서버가 user_id로 벡터를 찾아 씀 |
| 처리 — 게스트(비로그인) | 같은 방식으로 프로필 텍스트 합성 + 임베딩까지는 서버가 계산하지만 **DB에 저장하지 않고 벡터를 응답에 그대로 실어 클라이언트에 돌려줌**. 클라이언트는 내용을 몰라도 되는 opaque 값으로 localStorage에 보관했다가, 이후 지역 추첨(§3)·코스 생성(§4) 요청마다 그대로 함께 보냄 |
| 비즈니스 규칙 | **모든 질문에 답하지 않아도 진행 가능** — 미답변 항목은 중립으로 처리(데모 PRD 원칙: "많이 고른 사람이 안 고른 사람보다 과대표되지 않는다" 계승) · 로그인 사용자는 재응답(취향 재검사) 가능 — 새 응답이 기존 것을 덮어씀(히스토리는 `onboarding_responses`에 누적 보관, 최신 것만 현재 벡터에 반영) |
| 예외 | 완전 미응답으로 제출 → 저장은 허용하되 `user_taste_vectors` 생성은 보류(추천 시 §7의 "취향 없음" 폴백 적용) |

## 3. 지역 추첨

| 항목 | 내용 |
|---|---|
| 설명 | [추천] 버튼 → 도 → 시/군 2단계로 지역을 뽑는 "슬롯머신" 연출용 결과 반환 |
| 입력 | mode(`FULL_RANDOM` \| `PREFERENCE_WEIGHTED`), situation(선택) |
| 비즈니스 규칙 | `FULL_RANDOM`: 250개 시군구 균등 확률. `PREFERENCE_WEIGHTED`: 지역별 취향 적합도(그 지역 관광지들과 사용자 벡터의 평균 유사도)를 가중치로 한 **확률적** 추첨(최고 적합 지역이 매번 나오지는 않음 — 발견의 재미 유지) · **관광지가 없거나 준비도가 낮은 지역(최소 관광지 수 미달)은 추첨 후보에서 제외**(데모 `MIN_ATTRACTIONS` 게이트와 동일 원칙) |
| 예외 | 사용자 취향 벡터가 없는데 `PREFERENCE_WEIGHTED` 요청 → `FULL_RANDOM`으로 자동 폴백(에러 대신 우아한 대체) |
| 재시도 | 결과가 마음에 안 들면 다시 호출 가능(횟수 제한 없음 — MVP) |

## 4. 코스 생성 (슬롯 잠금 · 리롤 · 개수 조정)

### 4.1 코스 초안 생성
| 항목 | 내용 |
|---|---|
| 설명 | 추첨된 지역 기준으로 관광지 슬롯 N개를 채운 코스 초안 생성 |
| 입력 | regionId, transport, origin(출발지 좌표/주소), situation, stopCount(기본값 예: 4) |
| 비즈니스 규칙 | 관광지 후보는 `embedding_status='DONE'`인 것만(§7) · 유사도 상위권에서 **가중 랜덤 추출**(항상 top-N 고정이면 같은 지역에서 매번 같은 코스만 나옴 — 다양성 확보) · 슬롯 순서(order_index)는 출발지 기준 근사 동선 정렬(§7 "동선 계산" 방식 미확정, 저장 시점 1회 계산 원칙은 확정) |
| 예외 | 지역 내 준비된(embedding DONE) 관광지가 stopCount보다 적음 → 있는 만큼만 채우고 응답에 `actualStopCount` 명시 |

### 4.2 슬롯 잠금 / 리롤
| 항목 | 내용 |
|---|---|
| 설명 | 마음에 드는 슬롯은 잠금(유지), 나머지만 다시 뽑기 — 반복 가능 |
| 입력 | 현재 슬롯 전체(각 슬롯의 attractionId + locked 여부) |
| 비즈니스 규칙 | `locked=true` 슬롯은 그대로 응답에 재포함 · `locked=false` 슬롯만 새로 추천 · **이번 요청에 담긴 모든 attractionId(잠긴 것 포함)는 리롤 후보에서 제외**(직전에 본 걸 또 보여주지 않음) · 전부 잠그면(리롤 대상 0개) 그대로 반환 |
| 예외 | 리롤할 후보가 지역 내에 더 없음(다 소진) → 빈 슬롯 유지 + `exhausted: true` 플래그로 UI에 "더 이상 후보 없음" 표시 유도 |
| 저장 여부 | 이 단계는 서버에 영속화하지 않음(stateless, §5.3) — 새로고침하면 초안 소실, 확정 전까지는 가벼운 상태로 취급 |

### 4.3 개수 조정 / 수동 추가·삭제
| 항목 | 내용 |
|---|---|
| 설명 | 슬롯 개수를 늘리거나 줄이기, 특정 관광지를 검색해서 수동으로 끼워넣기/빼기 |
| 비즈니스 규칙 | 개수를 늘리면 늘어난 만큼 새 슬롯이 추천으로 채워짐(잠금 슬롯 영향 없음) · 수동 추가된 슬롯은 `source=MANUAL`로 표시(추천 슬롯과 구분, §6 DB) |
| MVP 포함 | 개수 조정은 포함, 검색 기반 수동 추가는 후속(관광지 검색 API가 별도 필요) |

## 5. 코스 확정 · 캘린더 연동

### 5.1 코스 확정
| 항목 | 내용 |
|---|---|
| 설명 | 슬롯 초안을 실제로 저장 — 이 시점부터 `trip_plans`/`trip_stops`로 영속화. **로그인 필수** — 이 API 자체가 v1의 유일한 로그인 요구 지점 |
| 게스트 처리 | 비로그인 상태에서 "저장"을 누르면 API를 호출하지 않고 로그인/회원가입 화면으로 전환 → 성공 후 클라이언트가 들고 있던 슬롯 상태 그대로 이 API를 호출(v1 구현 범위의 게스트→로그인 전환 참고). 별도 마이그레이션 엔드포인트 불필요 |
| 게스트 종료 | 로그인하지 않고 이탈하면 서버엔 아무 흔적도 안 남음 — `onboarding_responses`/`trip_plans` 어디에도 게스트 행은 생기지 않음(설계상 애초에 만들어지지 않음) |
| 비즈니스 규칙 | 확정 시점에 동선(순서)을 재계산해 고정(카카오모빌리티 같은 외부 API를 쓴다면 **이 1회만** 호출) · 확정 후에는 슬롯 잠금/리롤 불가 — 순서 변경/삭제만 가능(별도 "코스 수정" 흐름, 후속) |

### 5.2 캘린더 날짜 지정
| 항목 | 내용 |
|---|---|
| 설명 | 확정된 코스에 여행 시작/종료일 지정 |
| 비즈니스 규칙(안 — 미확정) | (a) 자체 캘린더: 같은 사용자의 CONFIRMED 코스와 날짜가 겹치면 **경고만 하고 차단은 안 함**(여행이 겹칠 수도 있는 실제 상황 존중, 강제 차단은 사용자 의도를 오판할 위험) · (b) 구글 캘린더 연동은 후속 — MVP는 (a)만 |
| 확정 필요 | 이 섹션은 설계 논의 중 — 실제 정책은 §9 결정 후 갱신 |

## 6. 친구 초대 · 같이 보기

| 항목 | 내용 |
|---|---|
| 설명 | 확정된(또는 확정 전) 코스를 링크로 공유해서 친구를 초대, 같이 보기 |
| 입력 | tripPlanId → 초대 링크 발급(토큰 기반, 만료시간 있음) |
| 비즈니스 규칙 | 초대 수락 시 로그인 필수(비회원 열람은 후속 검토) · 초대자(OWNER)만 초대 링크 재발급/무효화 가능 · 링크 만료 후 접근 시 "만료됨" 안내, 재발급 요청 유도 |
| 친구 목록(선택 기능) | 별도로 "친구 추가"(상호 수락) 기능도 제공 — 초대 링크와 별개로 자주 같이 가는 사람을 목록화 |
| MVP 포함 | 초대 링크 기반 공유는 포함, 친구 목록/상호 추가는 후속 |

## 7. 추천 시스템 (관광지 임베딩 · 콘텐츠 기반 매칭)

### 7.1 관광지 사전 임베딩 (배치)
| 항목 | 내용 |
|---|---|
| 설명 | 관광지 텍스트(name+category+region+tags+description)를 Ollama로 임베딩해 미리 저장 |
| 트리거 | 신규 등록/설명 갱신 시 `PENDING` 마킹 → 스케줄러가 주기적으로 처리 |
| 비즈니스 규칙 | description 없음은 상시 케이스(§3.1) — 절대 빈 텍스트 안 됨 · 텍스트 합성 규칙 변경 시 전체 재배치(`template_version` 관리) |
| 상세 | API-DESIGN-DRAFT §3.1 참고 (이 문서에서 중복 서술 안 함) |

### 7.2 사용자 취향 반영 매칭
| 항목 | 내용 |
|---|---|
| 설명 | 사용자 취향 벡터 vs 관광지 벡터의 코사인 유사도로 후보 필터링 |
| 비즈니스 규칙 | 최소 유사도 절대 임계값 + 사용자 자신의 최고 매칭 대비 상대 밴드(데모 `TravelerProfileService` 패턴 계승, 정확한 수치는 임베딩 모델 교체 후 재튜닝) · **유사도 점수/순위는 클라이언트에 노출하지 않음**(제품 원칙 — 랭킹을 보여주면 "1등이 아닌 곳"이라는 인식이 생겨 탐색의 재미가 줄어듦, 데모 PRD 원칙 계승) |
| 취향 없음 폴백 | 온보딩 미완료·응답 전무로 `user_taste_vectors`가 없는 사용자는 §3의 `FULL_RANDOM`과 동일하게 무작위 후보로 대체(추천이 아예 안 뜨는 것보다 나음) |
| 사용자 벡터 갱신 | 좋아요/저장(`user_interactions`) 발생 시 만족도 가중 평균으로 재계산(즉시 반영 — 별도 배치 불필요, 호출량이 적어 실시간 계산 가능) |

### 7.3 온보딩 재검사 시 벡터 재계산
| 항목 | 내용 |
|---|---|
| 설명 | 취향 재검사(§2) 완료 시 `user_taste_vectors`를 처음부터 다시 계산 |
| 비즈니스 규칙 | 기존 `user_interactions` 누적 이력은 유지 — 재검사 직후엔 온보딩 응답만 반영, 이후 상호작용이 다시 쌓이며 자연스럽게 보정 |

## 9. 아직 정책이 없는 것 (기능 명세에서도 비워둠)

이 항목들은 API-DESIGN-DRAFT §9와 동일 — 기능 규칙이 아직 결정되지 않아 위 섹션에도 "안(案)"으로만 표시했다:
1. 캘린더 중복 정책 — 경고만 할지, 특정 조건에서 차단도 할지
2. 완전랜덤/취향반영랜덤 기본값 — 사용자가 매번 고를지, 프로필 기본값을 둘지
3. 동선 계산 정밀도 — 실제 경로 API 기반 vs 단순 거리 근사
4. 친구 초대 링크의 비회원 접근 허용 여부
