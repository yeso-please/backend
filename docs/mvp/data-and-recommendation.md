# 데이터 이관·품질·추천·코스 조립 설계

상태: 팀 리뷰 전 초안. 이 문서는 데이터 이관이나 외부 API 호출을 실행하지 않는다. 관련 [흐름](flow.md), [API](api.md).

## 원천과 이관 경계

| 데이터 | 데모 원천 | MVP 처리 |
|---|---|---|
| 지역 250개 | `RegionSeeder`, `Region` | `SIG_CD` 유지, 중심 좌표/지도 코드 검증 |
| 관광지 | `Attraction`, TourAPI 동기화/상세 보강 | `sourceContentId` 기준 upsert, 설명·대표 이미지·좌표·운영정보의 원천과 수집일 저장 |
| 사용자/후기/여행 | H2의 데모 계정·작성 데이터 | 기본적으로 이관 제외. 실사용 데이터 여부 확인 뒤 별도 동의·검토 |
| 특산물·음식점·공식 코스 | 데모 DB/seed | MVP 핵심 관광지 코스에 필요할 때만 단계적 이관 |
| 지역 소개문 | TourAPI 전용 시군구 소개 필드 확인 안 됨 | 별도 검수 콘텐츠로 관리; 관광지 설명과 혼동 금지 |

현재 데모의 관광지 상세 보강은 `AttractionDetailBackfillService`/`AttractionDetailService`, 기존 수집은 `TourSyncService`, 태그 추론은 `ExperienceTags`를 참고한다. 2026-09-18 로컬 배치 종료 시 데모 DB 보고값은 관광지 테이블 12,164행, 상세 조회 완료 4,986행, 설명 확보 2,648행이었다. 이 값은 추천 가능 관광지 수와 다르며 이관 직전 다시 실측한다. `docs/DATA.md`의 2026-08 수치도 현재값으로 취급하지 않는다.

## 추천 가능 판정

관광지 행은 삭제하지 않고 다음 품질 상태를 별도로 둔다.

```text
recommendable = 유효한 지역 + 유효한 좌표 + 확인된 대표 이미지 + 임베딩 READY
description = 있으면 품질/추천 이유 향상, 없으면 이름·카테고리·태그 텍스트로 임베딩
```

사용자 요구로 **이미지 없는 관광지는 추천 제외**한다. URL 문자열이 있다는 것만으로 이미지 유효를 단정하지 않는다. 검증 시각·결과·저작권/출처 메타데이터를 저장한다. 외부 이미지 URL의 이용 조건은 콘텐츠별로 확인한다. 설명은 원천에도 없는 경우가 있으므로 필수 조건으로 두면 일부 지역이 비게 될 수 있다. 부족한 지역은 별도 보강·검수 목록에 넣는다.

`Attraction`에는 현재 이미지 필드가 없다. 이미지 URL, 검증 상태, 출처, 마지막 확인 시각을 새 스키마에 추가해야 한다. 지역 소개/카드도 현재 `Region` 엔티티에는 없으므로 별도 테이블 또는 관리 콘텐츠로 설계한다.

출시 게이트는 **고정 6곳이 아니라 지원하는 여행 일수와 리롤 여유로 계산**한다. 예를 들어 2박 3일에 관광지 2+3+2곳을 추천하고 하루당 대체 후보 2곳씩 제공하려면 최소 13곳이 필요하다. 이 수는 예시이며 실제 상한·하한은 데이터 분포를 측정해 정한다. 지역 카드에는 이미지 있는 랜드마크 최소 1곳이 필요하다. 게이트 미달 지역은 지도에 표시하되 추첨에서 제외하고, 운영 리포트에 부족 사유를 출력한다.

## 이관 절차와 검증

1. H2 파일을 서버 종료 상태에서 백업하고 스냅샷 식별자와 SHA-256을 기록한다.
2. PostgreSQL 스키마를 Flyway로 먼저 생성한다. `ddl-auto=validate`로 애플리케이션 기동을 검사한다.
3. `regions` → `attractions` → 이미지/임베딩 메타 순으로 staging에 적재 후 upsert한다. 원천 ID 중복·지역 코드 불일치는 격리 보고한다.
4. 테이블별 총계뿐 아니라 지역별 후보 수, 설명/이미지/좌표 교집합, 대표 샘플의 텍스트·좌표를 비교한다.
5. 이관 검증을 통과한 스냅샷에서만 임베딩 배치를 시작한다. 텍스트 변경은 `PENDING`으로 되돌린다.
6. 프로덕션 전환 전 RDS 스냅샷과 복구 리허설을 남긴다. 데모 DB를 원본처럼 계속 변경하면서 무계획 재이관하지 않는다.

## 임베딩

- 사용자와 관광지는 **같은 모델·모델 버전·텍스트 합성 버전**의 벡터만 비교한다.
- 온보딩은 답변 원본을 보존하고 프로필 문장을 만든 뒤 임베딩한다. 관광지는 이름·카테고리·지역·태그·설명으로 문장을 만든다.
- 임베딩 장애는 `FAILED`/재시도 가능 상태로 남기고 요청 시마다 재계산하지 않는다.
- 데모는 Ollama `bge-m3`와 BLOB 기반 애플리케이션 코사인 계산이다. MVP는 모델·텍스트 전처리·관광지 재임베딩 배치를 별도 Python 저장소로 분리한다. Python은 벡터 생성만 담당하고 Spring은 사용자·여행·원본 데이터·후보 점수·일정의 소유자다. Python이 RDS 업무 테이블을 직접 수정하지 않는다. 모델 교체 시 같은 버전의 사용자·관광지 벡터를 모두 재생성한다.
- 관광지 벡터는 사전 배치로 생성·검증해 적재한다. 온보딩 벡터 생성은 내부 인증된 Python API를 사용하되 짧은 타임아웃과 재시도 가능 상태를 둔다. 추첨·코스 리롤마다 Python을 동기 호출하지 않는다. 모델 장애 시 원본 답변은 저장하고 취향 점수만 제외해 진행한다. 자유서술과 위치는 불필요하게 로그에 남기지 않는다.
- RDS는 PostgreSQL을 권장한다. 지역·품질 조건으로 후보를 좁힌 뒤 Spring에서 코사인 유사도와 규칙 점수를 합산한다. 측정 결과 DB 검색이 필요하면 해당 RDS 버전의 `pgvector` 지원을 확인해 옮긴다. 첫 MVP부터 별도 벡터 DB나 Python 온라인 랭킹 서비스를 운영하지 않는다. 벡터 차원·모델/템플릿 버전·생성 시각을 저장한다.
- 온보딩 벡터가 없으면 지역 추첨과 코스 후보의 취향 점수만 제거한다. 여행 조건은 유지한다.

## 코스 조립 파이프라인

```text
지역·이미지·좌표 필터 → 취향·동행 조건 점수 → 충분한 후보 풀
→ 날짜별 가용시간 계산 → 점심/저녁·휴식시간 선점
→ 관광지 체류시간 + 구간 이동시간으로 채우기 → 운영정보·동선 검사
→ 초안 반환 → 사용자 잠금·교체 → 확정 전 재검증/경로 저장
```

1. **필터:** 지역 일치, 이미지·좌표·임베딩 준비, 중복·이미 본 후보 제외. 당일 휴무가 명확하면 해당 날짜에서 제외한다.
2. **점수:** 코사인 유사도는 후보 적합도의 한 항목이다. 이번 여행의 동행 관계·인원·이동수단·거리·카테고리 다양성을 별도 가중치로 둔다. 점수는 내부에서만 사용한다.
3. **시간 예산:** 날짜는 추첨 전에 필수다. 지역이 선택된 뒤 코스 생성 직전에 첫날 해당 지역 도착 시각·마지막 날 해당 지역 출발 시각을 간편 시간대 또는 정확한 시각으로 받는다. 미정이면 화면에 기본 가정을 보여주고 응답에 `estimated`를 표시한다. 첫날은 도착 이후, 마지막 날은 출발 이전만 배정한다. 하루에 관광지 수를 강제로 채우지 않고 `체류시간 + 이동시간 + 식사/휴식 + 여유시간` 합이 가용 시간을 넘지 않게 한다.
4. **식사:** MVP는 식당을 자동 지정하지 않고 점심·저녁 시간 슬롯을 확보한다. 기본 정책 예시는 점심 11:30–13:30, 저녁 17:30–19:30 범위에 각각 60–90분을 확보하는 것이다. 첫날 늦게 도착하거나 마지막 날 일찍 떠나면 해당 끼니는 제외한다. 데모의 음식점은 지역 대표성·운영시간 검증이 부족하고 특산물은 지역별 커버리지가 제한적이다. 검수된 출처·좌표·운영시간·메뉴가 있는 지역에 한해 후속 단계에서 선택형 식당/향토음식 제안을 붙인다. 단순 목록을 `맛집`이나 `지역 대표`라고 표기하지 않는다.
5. **체류:** 관광지별 실제 평균 체류시간 데이터가 없으면 유형별 기본값을 사용한다. 30분 포토스폿과 2시간 박물관을 같은 1개 슬롯으로 취급하지 않는다. 사용자가 `여유롭게/보통/빡빡하게`를 선택하면 체류·버퍼 계수를 조정한다.
6. **동선:** 후보 간 직선거리는 1차 거름망일 뿐 실제 이동시간이 아니다. 지역별 대표 이동시간 캐시 또는 선택된 소수 경로의 길찾기 조회로 초안의 상위 후보만 검증한다. 확정 시 자동차 여행은 카카오모빌리티 경로를 저장한다. 도보·대중교통에 자동차 소요시간을 사실처럼 제시하지 않는다. 이동수단별 경로 제공 범위가 다르면 정확도 등급을 응답에 표시한다.
7. **조립 방법:** 단순 점수순 나열 대신 시간창 제약이 있는 경로 문제로 취급한다. 작은 후보 풀에서 여러 시작 후보·방문 순서를 생성하고, `선호 적합도 + 다양성 − 이동시간 − 과밀` 목적함수로 상위 일정 몇 개를 비교한다. 운영시간 위반·일자 밖 방문·식사시간 침범은 점수 감점이 아니라 불가능 제약으로 처리한다.
8. **실패/완화:** 후보 부족은 실제 개수와 부족 이유를 반환한다. 운영시간 불확실은 경고를 붙인다. 동선 불가능하면 슬롯 수를 줄이고 프론트에 알린다. 서로 다른 지역 관광지를 몰래 섞지 않는다.
9. **편집:** 잠긴 슬롯은 유지한다. 교체 시 같은 날짜의 시간 예산과 전체 코스 중복을 다시 검사한다. 확정 후 장소·순서 변경도 같은 검증을 거친다.

`TripStop`에는 현재 일차/방문 날짜가 없으므로 `visit_date`와 일차 내 `order_index`를 추가해야 한다. 실제 출발/도착 시각을 MVP에서 보장하지 않는다면 시간표는 `estimated`로 표현한다.

## 테스트·운영 지표

- 250개 지역의 전체/추첨 가능/후보 부족 건수, 부족 사유 분포. 지원 여행 일수별로 최소 후보 수를 따로 측정한다.
- 이미지·좌표·설명·임베딩 각각의 보유율 및 교집합.
- 임베딩 모델/템플릿 버전별 `PENDING/DONE/FAILED`.
- 1일/2일/3일 여행의 중복 없음, 휴무일 충돌 없음, 시간 예산 초과 없음, 식사시간 침범 없음, 잠금 보존 테스트. 첫날 늦은 도착·마지막 날 이른 출발·아이 동반·경로 API 실패도 포함한다.
- 외부 TourAPI·길찾기 장애 시 폴백과 호출 예산 준수 테스트.

## 리뷰 결정

- PostgreSQL + Flyway 도입과 엔진 버전, `pgvector` 도입 시점을 정하기 위한 후보 수·지연시간 측정, Python 임베딩 실행 위치·비용.
- 이미지 원본 URL 참조와 별도 저장 중 어느 방식을 허락받고 운영할지.
- 설명 없는 관광지의 추천 허용 여부(기본안: 허용, 추천 이유는 검증된 태그/카테고리만 사용).
- 지역 도착/출발 시간의 미정 기본 가정·시간대 프리셋, 여행 일수·하루 방문 수 상한, 자동차 외 이동수단의 소요시간 표기 정책. 식당 자동 지정은 MVP 범위 밖으로 둔다.
