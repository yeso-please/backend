## 확인된 사실과 아직 제안인 것

| 구분 | 내용 |
|---|---|
| 확정 | 로그인/가입 → 최초 온보딩 → 날짜 선택 → 지도 추첨 → 지역 카드 → 코스 생성·수정 → 확정 |
| 확정 | 여행 시작일·종료일은 추첨 전에 필수. 기존 `CONFIRMED` 여행과 하루라도 겹치면 차단하고 확정 시 재검사 |
| 확정 | MVP는 이미지 없는 관광지를 추천에서 제외. 지역 카드는 관광지 원천 데이터와 별도 지역 소개 콘텐츠를 사용 |
| 사용자 방향 | MVP 소셜 로그인은 카카오만. 관광지 유사도뿐 아니라 동선·체류·이동·식사시간을 고려한 일정을 생성 |
| 권장 아키텍처 | RDS PostgreSQL. 별도 Python 저장소는 임베딩 생성·배치에 집중하고, 온라인 후보 점수/일정 조립은 Spring + PostgreSQL이 담당 |
| 제안 | 지역별 후보 수는 고정 6곳이 아니라 지원 여행 일수·리롤 여유로 계산. 시간 예산·식사 슬롯·운영정보 신뢰도·API 필드·오류 코드 |
| 권장 UX | 목적지를 모르는 추첨 전에는 날짜만 입력. 지역 선택 후 코스 생성 전에 첫날 도착·마지막 날 출발 시간을 간단히 입력 |
| 확인 필요 | 향토음식 선택지의 지역별 검증 범위, 실제 배포의 Python 실행 환경·비용 |

## 기존 문서와의 충돌

- `BUTTON-SPEC.md`의 게스트 온보딩·저장 시 로그인은 `FEATURE-SPEC.md`의 2026-09-17 로그인 우선 결정과 충돌한다. MVP에는 게스트 흐름을 넣지 않는다.
- `API-DESIGN-DRAFT.md`는 날짜 확인 API를 정의하지만 추첨·초안 요청에 날짜가 빠져 있다. 이 초안은 날짜를 모든 여행 맥락 요청에 포함한다.
- `FEATURE-SPEC.md`는 초안 생성 때 자동차 길찾기로 정렬하면서 확정 시 1회 호출 원칙도 적고 있다. 이 초안은 초안에서 좌표 기반 근사, 확정에서 외부 경로 검증으로 구분한다.
- 현재 `Attraction` 엔티티에는 이미지 URL 필드가 없고, `TripStop`에는 방문 날짜/일차가 없다. 다일 코스와 이미지 필수 정책을 구현하려면 스키마 변경이 필요하다.
- 현재 설정은 SQLite + `ddl-auto: update`이다. 공유 개발/운영 RDS 도입 전 PostgreSQL + Flyway로 전환하는 것은 **제안**이며 팀 승인 후 구현한다.

## 리뷰 방법

각 문서의 `리뷰 결정` 항목에 대한 팀 코멘트를 먼저 모은다. 합의된 값만 기존 문서와 API 계약에 반영한다. 그 전에는 에이전트에게 이 초안을 구현 완료된 API로 가정하지 말라고 지시한다.
