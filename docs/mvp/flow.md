# MVP 기능 명세

상태: 제품 결정 반영, 구현 전. 세부 API는 [api.md](api.md), 계산 규칙은 [data-and-recommendation.md](data-and-recommendation.md)를 따른다.

## F1. 로컬 회원가입·로그인

- 이메일·비밀번호·닉네임으로 가입하고 즉시 JWT를 발급한다. 이메일 중복은 409, 인증 실패는 계정 존재 여부를 숨기는 동일 401을 반환한다.
- access token은 짧게 유지하고 refresh cookie로 회전한다. 로그아웃은 refresh token을 폐기한다.
- 로그인 응답의 `onboardingCompleted`로 첫 화면을 정한다. 소셜 로그인은 MVP에 없다.

완료 기준: 가입/로그인/refresh/logout 정상·중복·실패·토큰 재사용 통합 테스트가 있다.

## F2. 온보딩과 재검사

- 서버가 [온보딩 질문 계약](onboarding-questionnaire.md)의 버전된 여행 MBTI 12문항과 경험 태그·제외 조건 목록을 제공한다.
- 사용자는 12개 답, 경험 태그 최대 5개, 제외 조건, 좋았던 여행지 0~30개를 한 제출로 저장한다. 12개 답은 모두 필수다.
- 일정 밀도 `RELAXED`(하루 최대 4곳) 또는 `PACKED`(최대 6곳)도 필수로 고른다. MBTI 계산과는 분리해 저장한다.
- 결과에는 MBTI 코드와 프로필 문장, 임베딩 상태가 포함된다. 임베딩 실패도 제출·온보딩 완료를 되돌리지 않는다.
- 프로필의 `여행 성향 다시 검사`는 같은 질문을 열고 새 제출을 만든다. 추천은 최신 완료 제출만 사용한다.
- 초대 손님도 같은 문항에 답하지만 사용자 계정이 아닌 초대 참여자에 귀속한다.

완료 기준: 질문 버전 불일치, 답 누락, 태그 상한, 중복 여행지, 재검사 이력, 임베딩 장애를 테스트한다.

## F3. 여행 맥락과 친구 초대

- 소유자는 시작일, 0~6박, 이동수단, 출발 위치(선택)를 정한다. 종료일은 서버가 계산한다.
- 확정 여행과 겹치는 날짜는 캘린더에서 비활성화한다. 서버도 생성·변경 시 동일한 검사를 수행해 중복 여행을 거부한다.
- 소유자는 추첨 전이나 코스 확정 후 초대 링크를 만들 수 있다. 권한은 `VIEW` 또는 `EDIT`, 기본 만료는 7일이다.
- 프론트는 링크 복사와 카카오톡 공유 버튼을 제공한다. MVP 서버는 카카오 친구 목록이나 메시지 API를 호출하지 않는다.
- 최초 일정 생성은 회원 소유자만 할 수 있다. 손님이 초대 링크를 열어 표시 이름과 온보딩을 완료하면 `READY`가 되고, 추첨 시 `COMPANION_TASTE`를 체크한 경우에만 반영한다.
- 손님에게 공유되는 완성 일정은 기본 VIEW다. 소유자가 링크별 권한을 EDIT로 바꿀 수 있으며 회원가입은 요구하지 않는다.
- 상세 일정 공유 링크는 로그인 없이 접근할 수 있다. EDIT 토큰 소지자는 장소·순서·식당만 바꿀 수 있으며 날짜·소유권·초대 권한은 바꾸지 못한다.

완료 기준: 만료/폐기/잘못된 토큰, VIEW 수정 거부, EDIT 허용 범위, 초대 손님 성향 포함/제외를 테스트한다.

## F4. 지도·지역 추첨

- 지도는 250개 `SIG_CD` 지역과 요청 여행 일수별 `drawEligible`을 표시한다.
- `FULL_RANDOM`은 적격 지역에서 균등 추첨한다. `CONDITIONAL`은 사용자가 고른 `DISTANCE`, `MY_TASTE`, `COMPANION_TASTE` 요소만 점수에 넣고 확률적으로 추첨한다.
- 조건을 하나도 고르지 않은 CONDITIONAL은 400이다. 필요한 위치·성향이 없으면 그 요소를 무시하고 `ignoredConditions`로 알린다.
- 리롤은 같은 요청을 다시 실행한다. 이전 지역 제외 목록을 관리하지 않아 같은 지역이 연속으로 나올 수 있다.
- 여행 생성 단계에서 날짜 겹침을 차단하므로 추첨 요청은 유효한 trip만 받는다. 확정 직전에는 경쟁 상태 방지를 위해 한 번 더 검사한다.

완료 기준: 균등성 단위 테스트, 조건별 점수, 위치/벡터 없음, 후보 없음 422, 같은 지역 재등장을 테스트한다.

## F5. 지역 카드

- 지역명, 2~4문단 소개, 대표 이미지, 역사·특성 태그, 랜드마크 1~3개, 출처·갱신일을 반환한다.
- 소개는 사실 근거로 생성되고 사람이 승인한 콘텐츠만 공개한다. 관광지 상세를 지역 공식 소개처럼 재사용하지 않는다.
- 소개·대표 이미지가 없거나 여행 일수에 맞는 추천 가능 관광지가 부족하면 카드와 추첨 대상에서 제외하고 품질 리포트에 이유를 남긴다. 사용자 화면에 임시 허구 폴백을 만들지 않는다.

완료 기준: 승인 상태, 출처, 이미지 검증 실패, 기간별 후보 부족을 테스트한다.

## F6. 코스 생성

- 지역 선택 뒤 첫날 지역 도착/마지막 날 지역 출발 시각을 받는다. 생략 시 12:00/17:00을 사용하고 당일은 12:00~20:00으로 가정한다.
- 일정 밀도는 여행 요청에서 바꿀 수 있으며 생략하면 소유자의 온보딩 값을 쓴다. RELAXED 최대 4곳, PACKED 최대 6곳이지만 시간 제약을 깨면서 채우지 않는다.
- 개인과 READY 동행자의 취향 점수, 카테고리 다양성, 이동 추정, 단순 체류 슬롯, 식사시간을 함께 고려한다. 운영시간 위반과 일정 중복은 불가능 제약이다.
- 점심 12:00~13:00, 저녁 18:00~19:00을 기본으로 하되 사용자가 바꿀 수 있다. 여행 시간 밖 끼니는 생략한다.
- Python 장애 시 적재된 TourAPI 공식 코스를 우선 사용하고, 없으면 비개인화 규칙 코스를 사용한다.
- 장소와 순서가 정해진 후 LLM이 사실 기반 감성 제목만 만든다. LLM 실패는 일정 생성 실패가 아니다.

완료 기준: 0~6박, 당일 8시간, 첫/마지막 날, 두 일정 밀도와 목표 미달, 식사 침범, 후보 부족, 임베딩/LLM 장애를 테스트한다.

## F7. 코스 편집·식당 선택

- 각 관광지 슬롯에서 현재 코스에 없는 같은 지역 관광지를 `자연/역사·문화/체험·레포츠/산책·휴식/기타`로 나눠 추천한다.
- 지도에서 추천 가능 관광지를 핀으로 탐색한다. 이름·대표 썸네일을 표시하고 상세 패널에서 설명·유형·체류시간을 본 뒤 일정에 직접 추가할 수 있다.
- 추가·교체·삭제·순서 변경 뒤 시간·중복·이동·밀도 상한을 다시 계산한다. 초안은 여행마다 서버에 저장하고(버전 관리), 편집할 때마다 서버가 전체 일정을 검증한다.
- 식당은 TourAPI `contentTypeId=39`를 우선 추천하고 공공 지정 식당으로 보완한다. 식사 슬롯의 카카오 주변검색 기준점은 직전 관광지이며 첫 항목이면 지역 중심 좌표를 쓴다.
- 사용자가 식당을 고르면 외부 ID, 이름, 주소, 좌표, 카테고리, 외부 URL, 확인된 대표메뉴와 근거 출처를 스냅샷 저장한다. 없는 메뉴·평점·인기를 생성하지 않는다.

완료 기준: 유형 필터, 코스 내 장소 제외, 기준점 없음, 카카오 장애, 식당 선택/제거를 테스트한다.

## F8. 확정·조회·공유

- 확정 시 서버가 지역·관광지 품질·방문 날짜·중복·시간·권한을 다시 검사한다.
- 확정 직전에 겹치는 여행이 생겼으면 409로 차단한다. 확인 값으로 우회할 수 없다.
- 멱등성 키로 중복 저장을 방지한다. 확정 후 소유자/EDIT 손님은 장소·순서·식당을 수정할 수 있다. 날짜 범위 변경은 새 여행 생성으로 처리한다.
- 조회자는 로그인 사용자 소유권 또는 유효한 공유 토큰으로 권한을 얻는다. 토큰 원문은 로그·DB에 저장하지 않는다.

완료 기준: 날짜 중복 차단, 동시 확정, 멱등성, VIEW/EDIT 권한, 토큰 만료·폐기를 테스트한다.

## 후속 기능

카카오 로그인·직접 메시지 발송, 친구 계정 연결, 실시간 공동 편집, 대표 메뉴 데이터 보강, 정밀 체류시간, 외부 길찾기 확정 정책은 MVP 이후 별도 명세로 다룬다.
