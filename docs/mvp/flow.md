# MVP 사용자 흐름과 기능 규칙

상태: 팀 리뷰 전 초안. 관련 [API](api.md), [데이터·추천 설계](data-and-recommendation.md).

## 1. 로그인·회원가입

- 모든 MVP 여행 API는 로그인 필요. 비회원은 로그인/가입 화면으로 이동한다.
- MVP의 회원가입·로그인은 카카오 계정으로 시작한다. 이메일/비밀번호 가입은 기존 구상에 있으나 이번 범위에서 제외한다.
- 로그인 응답에는 `onboardingCompleted`를 포함해 프론트가 다음 화면을 결정한다. 온보딩 완료 여부는 별도 DB 필드 또는 최신 제출의 존재로 판정하되 빈 응답 제출도 완료로 취급한다.
- MVP 소셜 로그인 제공자는 **카카오 하나**다. 구글은 후속으로 미룬다. 카카오에서 돌아온 인가 코드는 백엔드가 교환하고 카카오 사용자 ID로 계정을 찾는다. 동일 이메일의 기존 계정을 자동 병합하지 않는다.

## 2. 온보딩

- 최초 로그인 후 미완료자만 진입한다. MBTI형 여행 성향, 좋았던 여행지(지역/장소 식별자 또는 자유서술), 선호 태그를 받는다.
- 질문 일부를 건너뛸 수 있고 완전 미응답 제출도 완료로 저장한다. 미답변을 음수 취향으로 해석하지 않는다.
- `submissionId`로 제출 묶음을 보존한다. 현재 취향 계산은 마지막 제출 묶음만 사용한다. 명시적 재검사 외에는 기존 결과를 변경하지 않는다.
- 임베딩 서비스 장애 시 원본 응답 저장과 온보딩 완료는 유지하고 벡터를 `PENDING`으로 재시도한다. 벡터가 없으면 조건 기반 추첨에서 취향 가중치를 제외한다.

## 3. 날짜 선택

- `startDate`와 `endDate`는 한국 달력 날짜(`YYYY-MM-DD`), 양끝 포함이다. 시작일이 종료일 이후면 400.
- 기존 확정 여행과 `[새 시작일 ≤ 기존 종료일] && [기존 시작일 ≤ 새 종료일]`이면 하루라도 겹치는 것으로 판정한다.
- 프론트는 다음 화면 진입 전에 날짜 확인 API를 호출한다. 서버는 코스 확정 트랜잭션에서 재검사한다. 사전 확인만으로 날짜를 예약하지 않는다.
- 취소/삭제된 여행은 차단 대상에서 제외한다. 확정 후 날짜 변경은 MVP에서 허용하지 않는다.
- 동시 요청이 각각 사전 확인을 통과하는 경쟁을 막도록 사용자 단위 잠금 또는 DB 수준 직렬화 전략을 구현하고 통합 테스트한다.

## 4. 메인 지도와 지역 추첨

- 지도는 `SIG_CD` 기준 250개 지역을 표시한다. 실제 지도 경계/애니메이션은 프론트 책임이며 서버는 지역 목록·추천 가능 상태·추첨 결과를 준다.
- 날짜 선택 후 추첨 모드(`FULL_RANDOM`/`PREFERENCE_WEIGHTED`), 선택적 출발 위치, 이동수단, 동행 인원·관계, 기타 선호를 입력한다. 위치 미동의 시 좌표는 보내지 않아도 된다.
- `FULL_RANDOM`은 **추천 가능한 지역 집합에서 균등** 추첨한다. 250개 전부를 노출하려면 각 지역에 충분한 이미지·좌표·추천 후보를 준비해야 한다. 준비 안 된 지역을 추첨해 빈 코스를 보여주지 않는다.
- `PREFERENCE_WEIGHTED`는 취향·출발 거리·여행 일수·동행 조건을 반영하되 확률적으로 뽑는다. 취향 벡터가 없으면 취향 가중치만 제거하며, 다른 조건까지 무시하지 않는다.
- 재추첨은 동일 API 재호출. 직전 지역 제외는 요청의 `excludeRegionIds`로 표현한다. 후보가 1곳뿐이면 제외를 완화하고 응답에 `relaxedExclusions`를 명시한다.
- 추첨 결과가 도착하면 프론트가 슬롯 애니메이션을 끝내고 최종 지역을 표시한다. API 호출마다 애니메이션 프레임을 보내지 않는다.
- 추첨 전에는 목적지가 정해지지 않았으므로 정확한 도착·출발 시간을 묻지 않는다. 지역을 선택한 뒤 코스 생성 화면에서 첫날 지역 도착 시각과 마지막 날 지역 출발 시각을 간단히 받는다.

## 5. 지역 카드

- 선택 지역의 이름·검수된 소개문·대표 이미지·랜드마크 1~3곳을 반환한다. 관광지 `overview`를 지역 전체의 공식 소개문으로 표시하지 않는다.
- 소개문과 랜드마크마다 출처·갱신 시각을 관리한다. 소개문이 검수 전이면 사실 기반 짧은 템플릿으로 폴백한다.
- 이미지 URL이 깨졌거나 빈 랜드마크는 카드 후보에서 제외하고 다음 후보를 사용한다.

## 6. 코스 초안·편집·확정

- 선택 날짜 수에 맞춰 일자별 관광지 슬롯을 만든다. 첫날/마지막 날은 이동 여유를 두고 중간 날보다 적게 배치할 수 있다.
- 관광지 방문 사이에 점심·저녁 식사와 휴식 시간을 별도 일정 항목으로 확보한다. 첫날 지역 도착·마지막 날 지역 출발 시각을 입력받되, `아직 몰라요`를 허용한다. 이 경우 명시된 기본 가정과 `estimated` 표시를 응답에 포함한다.
- 식당 자체는 MVP의 핵심 추천 대상이 아니다. 검증된 지역 음식/향토음식 근거가 있는 경우에만 식사 슬롯에 선택지를 제시한다. 그렇지 않으면 주변 식사시간만 확보하고 특정 식당을 `맛집`·`현지 대표`로 단정하지 않는다.
- 추천 점수는 후보 선정에 쓰고, 일정은 운영시간·휴무·체류시간·거리·중복 여부를 별도로 검증한다. 불명확한 운영정보는 `확인 필요`로 표시하고 확정적 일정으로 말하지 않는다.
- 초안은 서버 DB에 저장하지 않는다는 기존 설계를 유지한다. 클라이언트가 현재 일자·순서·잠금 상태·이미 본 관광지 ID를 다음 요청에 보낸다.
- 사용자는 슬롯 잠금, 잠기지 않은 슬롯만 재추천, 장소 삭제/순서 변경, 하루 방문 수 조정을 할 수 있다. 검색 기반 임의 관광지 추가는 후속 후보로 둔다.
- 추천 후보가 소진되면 빈 슬롯과 `exhausted=true`를 반환한다. 다른 지역 관광지를 조용히 섞지 않는다.
- 확정 API는 클라이언트의 지역 소속·중복·이미지·좌표·일차 범위·일정 겹침을 재검증하고 저장한다. 확정된 코스는 본인만 조회/수정한다.

## 리뷰 결정

1. `FULL_RANDOM`이 250개 모두여야 하는지, 출시 시 추천 가능한 지역만 포함해도 되는지.
2. 재추첨 시 직전 1개만 제외할지, 세션 중 이미 본 모든 지역을 제외할지.
3. 초안 새로고침 복구를 프론트 로컬 저장으로 지원할지.
4. 취소된 여행을 복원할 때 기존 여행과 날짜가 겹치면 어떻게 할지(기본안: 복원 차단).
5. 지역별 향토음식 선택지를 별도 검수 콘텐츠로 어느 범위까지 준비할지. 기본안은 근거가 있는 지역에만 선택지 표시.
