# 초기 세팅과 3인 팀 작업 순서

상태: 팀 리뷰 전 초안. 데모 저장소는 **읽기 전용 참고**, 이 저장소만 수정한다. 관련 [흐름](flow.md), [API](api.md), [데이터·추천](data-and-recommendation.md).

## 사용자가 먼저 깔아둘 범위

기준은 완성된 추천 알고리즘이 아니라 **로그인부터 코스 확정·재조회까지 하나의 통합 테스트가 통과하는 세로 슬라이스**다.

1. 팀이 이 초안의 리뷰 결정을 확정하고 기존 문서의 모순을 정리한다.
2. Java 21/Gradle 실행, PostgreSQL 로컬 Compose, 환경별 설정, Flyway, `ddl-auto=validate`, Testcontainers 통합 테스트, CI, 공통 오류/인증, OpenAPI 초안을 설치한다. 실제 RDS 접속 정보는 Git에 넣지 않는다. 카카오 로그인을 MVP 인증 경로로 연결한다.
3. 데모 DB에서 개인정보를 제외한 지역·관광지 이관 스크립트와 2~3개 지역의 작고 재현 가능한 개발 seed를 제공한다. 전체 데이터와 이미지·임베딩은 별도 배치로 적재한다.
4. 카카오 로그인, 온보딩 원본 저장, 날짜 겹침 검사, 균등 지역 추첨, 지역 카드, 규칙 기반 코스 초안/확정/재조회가 실제 DB를 사용해 한 번 이어지게 만든다.
5. 지역 선택·관광지 후보·일정 조립·임베딩 공급자·외부 길찾기를 분리해 팀원이 구현을 교체할 수 있게 한다. 빈 인터페이스만 만들고 기능이 통과하지 않는 상태로 인계하지 않는다.

구글 로그인, 정교한 취향 점수, 전국 이미지·설명 품질 완성은 위 기반의 완료 조건이 아니다. 카카오 로그인은 MVP에 포함한다. 단 프론트 통합에 필요한 요청/응답 형태는 먼저 고정한다.

## 병렬 담당 범위

| 담당 | 소유 범위 | 선행 조건 | 완료 기준 |
|---|---|---|---|
| 초기 세팅 담당(사용자) | 인증·DB·migration·공통 계약·데이터 이관·세로 슬라이스·통합 리뷰 | 팀의 계약 승인 | 신규 팀원이 로컬에서 테스트와 전체 흐름을 실행 가능 |
| 백엔드 A | 온보딩 질문/취향 텍스트, 조건 기반 지역 추첨, 지도·지역 카드 | 인증·Region/Attraction 계약 | 위치 없음/벡터 없음/후보 부족/리롤 테스트 포함 |
| 백엔드 B | 관광지 품질·Python 임베딩 공급 연동, Spring 내 후보 점수·검색, 식사·체류·이동을 반영한 날짜별 코스 조립·편집 | 데이터 이관·코스 API 계약 | 일자·식사·운영시간·중복·잠금·외부 장애 테스트 포함 |

같은 엔티티나 migration을 둘 이상이 동시에 수정해야 하면 먼저 짧은 계약 PR로 필드·API를 합의한다. A/B 작업은 각각 `docs/features/`의 작업 명세와 `docs/api/`의 계약 파일을 먼저 만들고, 코드와 테스트를 같은 PR에서 제출한다.

## 구현 순서와 검증 게이트

| 단계 | 산출물 | 통과 게이트 |
|---|---|---|
| 0. 설계 리뷰 | 이 폴더의 미결정 확정, 기존 문서의 충돌 해결 | 프론트·백엔드가 동일한 날짜/추첨/코스 요청 예시 승인 |
| 1. 기반 | PostgreSQL/Flyway/CI/인증/오류/개발 seed | clone → 로컬 서버 기동 → `test` 통과; 비밀값 미커밋 |
| 2. 세로 슬라이스 | 실제 DB의 카카오 로그인→온보딩→날짜→추첨→코스 저장 | 정상·인증 실패·겹침 409 통합 테스트 |
| 3. 병렬 기능 | A 지역/취향, B 관광지/일정 | 각 PR의 계약 테스트와 실패 경로 테스트 통과 |
| 4. 데이터 품질 | 전체 지역/관광지 이관·추천 가능 리포트 | 지역별 후보 게이트 및 출처·이미지 검증 |
| 5. 출시 리허설 | dev RDS·프론트 연동·복구 시험 | 데이터 대조, 대표 사용자 흐름, 외부 API 장애, 백업 복구 |

## 에이전트에 줄 작업 지시 형식

```text
이 저장소의 docs/mvp/README.md부터 읽고 담당 범위의 flow.md, api.md,
data-and-recommendation.md, delivery.md 및 docs/conventions/을 확인한다.
현재 문서는 구현 전 초안이므로 실제 코드와 다른 부분을 먼저 보고한다.
담당 기능의 docs/features/ 작업 명세와 docs/api/ 계약을 작성한 뒤,
그 범위의 코드·migration·테스트만 변경한다. demo 저장소는 읽기만 한다.
새로 필요한 제품 결정은 임의로 확정하지 말고 PR에 선택지와 권장안을 남긴다.
완료 시 실행한 테스트, API 예시, 데이터 변경, 남은 리스크를 요약한다.
```

## 리뷰 결정

1. 카카오 OAuth 콜백·토큰 전달 방식과 구글 로그인 후속 일정.
2. PostgreSQL 엔진 버전과 `pgvector` 도입 시점, Python 임베딩 배치/API의 배포 환경·비용.
3. 지역별 여행 일수에 따른 후보 품질 게이트와 부족 지역 처리.
4. 식당 자동 지정은 MVP 제외. 지역 선택 후 입력받는 첫날 도착·마지막 날 출발 시간대와 미정 시 기본 가정.
5. 프론트와 API 계약 동결 시점.
