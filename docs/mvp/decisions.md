# MVP 확정 제품 결정

작성일: 2026-09-20. 아래 항목은 팀원이 재논의부터 시작하지 않고 구현하는 기본값이다. 구현 불가능·보안·데이터 손실 문제가 있을 때만 근거와 대안을 PR에 남긴다.

## 인증과 온보딩

- 이메일, 비밀번호, 닉네임을 사용하는 로컬 회원가입·로그인만 제공한다. 비밀번호는 BCrypt로 저장한다.
- access token은 응답 body, refresh token은 `HttpOnly; Secure; SameSite=Lax` 쿠키로 전달한다. 개발 HTTP에서는 Secure만 환경별 해제한다. refresh token은 해시 저장·회전한다.
- 온보딩은 데모의 여행 MBTI 12문항(각 1/2 선택), 경험 태그 최대 5개, 제외 조건, 좋았던 여행지 기록으로 구성한다. 질문은 버전 관리하며 답변 원본과 계산 결과를 함께 저장한다.
- MBTI와 별도로 일정 밀도 `RELAXED`(하루 최대 4곳) 또는 `PACKED`(최대 6곳)를 필수로 고른다. 기본 선호로 저장하되 여행마다 바꿀 수 있다.
- 좋았던 여행지는 지역 `SIG_CD`, 선택적 메모·태그로 저장하며 같은 제출에서 중복 지역을 허용하지 않는다. 0~30개를 허용한다.
- 최초 로그인 후 미완료자에게 온보딩을 보여주고, 이후 프로필의 `여행 성향 다시 검사`에서 새 제출을 만든다. 과거 제출은 삭제하지 않고 최신 완료 제출만 추천에 사용한다.

## 여행과 추첨

- 사용자는 시작일과 `nights`를 고른다. `endDate = startDate + nights`, `days = nights + 1`이다. 당일치기는 0박 1일, MVP 상한은 6박 7일이다.
- 기존 확정 여행과 겹치는 날짜는 캘린더에서 선택할 수 없다. 서버도 여행 생성·날짜 변경·최종 확정 시 다시 검사해 409 `TRIP_DATE_OVERLAP`으로 차단한다. acknowledgement로 우회하지 않는다.
- 완전 랜덤과 조건 기반 랜덤을 버튼 옆에서 선택한다. 조건 기반은 `DISTANCE`, `MY_TASTE`, `COMPANION_TASTE` 체크박스를 독립 선택한다. 날짜/기간은 항상 후보 가능성에 반영한다.
- 지역 리롤은 이전 지역을 자동 제외하지 않는다. 같은 지역이 연속으로 나올 수 있다.
- 여행 친구는 회원이 아니어도 된다. 소유자가 초대 링크를 만들고 프론트의 카카오톡 공유 버튼 또는 링크 복사로 전송한다. 서버가 카카오 친구에게 직접 메시지를 보내지 않는다.
- 초대받은 사람은 표시 이름과 동일 온보딩을 제출한다. 참여자 성향은 초대 상태가 `READY`일 때만 반영하고, 개인별 점수를 평균해 한 사람의 취향이 압도하지 않게 한다.
- 최초 여행 방·추첨·코스 생성은 회원 소유자만 할 수 있다. 손님에게 완성 일정을 공유할 때 기본 권한은 VIEW이며 소유자가 링크별로 EDIT로 변경할 수 있다. 손님 가입은 강제하지 않는다.

## 지역·관광지 품질

- 지역은 검수 완료 소개문, 검증된 대표 이미지, 해당 여행 일수에 충분한 추천 가능 관광지가 있어야 추첨 가능하다.
- 추천 가능 관광지는 유효한 지역·좌표·상세 설명·검증된 이미지가 모두 있어야 한다. 부족 필드는 품질 리포트에 기록하고 추천에서 제외한다.
- 필요한 관광지 수는 `days × 일정 밀도 상한 + min(days, 3)`이다. RELAXED는 일 4곳, PACKED는 일 6곳과 교체 후보를 확보한다. 긴 여행에서 기준을 못 채우는 지역은 해당 요청에만 제외한다.
- 지역 소개문은 지역 역사·특성·대표 여행지를 근거 데이터로 합성한 2~4문단의 감성 문장이다. LLM 사용 시 입력 근거와 모델 버전을 저장하고 사람이 승인해야 공개한다. 근거가 없거나 미승인인 지역은 추천하지 않는다.

## 일정과 편집

- 도착/출발 시각 미입력 기본값은 첫날 12:00, 마지막 날 17:00이다. 당일치기는 12:00~20:00로 설정한다.
- 하루 관광지는 RELAXED 최대 4개, PACKED 최대 6개다. 실제 체류 통계 대신 유형별 기본 슬롯(짧은 장소 60분, 일반 90분, 대형 문화·레포츠 120분)을 사용하고 `estimated`를 표시한다. 시간 제약상 목표를 채울 수 없으면 장소를 억지로 넣지 않고 경고한다.
- 점심 기본 슬롯은 12:00~13:00, 저녁은 18:00~19:00이다. 사용자가 시간을 바꿀 수 있다. 가용 시간 밖 끼니는 만들지 않는다.
- 식당 추천은 같은 지역의 TourAPI 음식점(`contentTypeId=39`)을 1순위로 사용한다. 농촌진흥청 농가맛집·지자체 모범/향토음식점·착한가격업소처럼 지정 근거가 있는 공공데이터를 보완 후보로 쓰고, 직전 관광지 좌표 기준 카카오 Local `FD6` 검색을 fallback으로 제공한다.
- 식당에는 출처와 추천 근거 label을 표시한다. 원천이 제공한 대표메뉴만 노출하며 카카오 결과에서 맛·평점·인기·대표메뉴를 추론하지 않는다. 선택 결과는 이름·주소·좌표·외부 URL·카테고리·확인된 메뉴·출처를 일정 스냅샷에 저장한다.
- 지역 음식·특산물은 출처가 있는 후보를 수집하고 사람이 승인한 항목만 검색 chip과 추천 이유에 사용한다.
- 코스에 없는 같은 지역 관광지를 유형별 대체 후보로 보여준다. 사용자/동행 성향 점수, 이미지·설명·좌표, 현재 일정과의 중복·이동을 다시 검사한다.
- 같은 지역의 추천 가능 관광지를 지도 핀으로 보여준다. 핀에는 이름·대표 썸네일을 표시하고 상세 패널에서 설명·유형·예상 체류시간을 확인한 뒤 일정에 직접 추가할 수 있다. 추가·교체·삭제·이동마다 서버가 전체 일정을 재검사한다.
- 공유 링크는 만료 가능한 난수 토큰이며 DB에는 해시만 저장한다. 소유자가 `VIEW` 또는 `EDIT` 권한으로 발급·변경·폐기한다. 편집자는 여행 날짜·소유자·공유 권한을 바꿀 수 없다.

## 외부 서비스와 폴백

- 외부 길찾기 실패 정책은 최종 결정 전이다. 그 전까지 직선거리 기반 추정값과 경고를 반환하며 실제 경로라고 표현하지 않는다.
- Python 임베딩 장애 시 RDS에 미리 적재된 해당 지역의 TourAPI 공식 코스를 기간에 맞게 자른다. 공식 코스가 없으면 취향 점수를 제외한 규칙 기반 코스를 만든다. 둘 다 불가능하면 422와 부족 이유를 반환한다.
- LLM은 코스 장소·순서를 결정하지 않고 제목 생성만 맡는다. 장소·지역·계절 등 검증된 입력만 사용한다. 실패 시 `{지역명}, {대표 테마}를 따라 걷는 {일수}일` 형식으로 폴백한다.

## MVP 이후 논의

카카오 로그인, 카카오 메시지 API를 통한 서버 직접 발송, 친구 계정 전환/병합, 사용자 리뷰·평점 기반 맛집 순위, 외부 길찾기 확정 정책, 실측 체류시간, 실시간 공동 편집은 MVP 이후다.

## 여행기·사진 지도·친구 공개

- 확정 코스 하나에 여행기 하나를 연결한다. 여행기는 사진 1~30장, 제목·본문, 만족 태그/점수와 함께 초안·발행 상태를 가진다.
- 여행기 지도는 내가 남긴 여행의 회고용이다. 핀에는 여행기 대표 사진과 확정 코스 제목을 썸네일로 표시하고, 핀을 누르면 해당 여행기와 사진을 연다. 전체 지도를 제3자에게 공개하지 않는다.
- 공개 범위는 `PRIVATE`, 수락된 친구만 보는 `FRIENDS`, 만료·폐기 가능한 읽기 전용 `LINK`다. 친구 공개는 친구 요청이 상호 수락된 뒤에만 성립한다.
- 사진 위치의 기본 공개 정밀도는 `CITY`다. 사용자는 `EXACT|CITY|HIDDEN`으로 바꿀 수 있다. EXIF 전체와 원본 파일명은 외부 응답에 내보내지 않는다.
- 발행된 여행기의 지역·확정 장소 카테고리·사용자 선택 만족 태그/점수만 낮은 가중치의 취향 신호로 쓴다. 자유 본문, 사진 분석, EXIF, 열람 수는 추천에 사용하지 않으며 사용자는 취향 반영을 끌 수 있다.
