# 문서화

## 목적

프로젝트의 요구사항, API 계약, 설계 결정, 작업 상태는 저장소의 Markdown을 기준으로 관리합니다. 외부 문서는 논의 창구로 사용할 수 있지만, 구현에 필요한 최종 정보는 반드시 저장소에 남깁니다.

문서는 사람이 읽기 쉬워야 하며 에이전트가 검색·분석하기 쉬워야 합니다. 한 문서에는 한 가지 목적만 둡니다. 현재 상태와 결정된 사실을 추측이나 대화 기록과 섞지 않습니다.

## 문서 종류와 위치

```text
docs/
├── README.md                 # 문서 읽기 순서와 인덱스
├── api/                      # 구현된 REST API reference
├── features/                 # 기능별 작업 명세와 완료 기준
├── adr/                      # 중요한 설계 결정
├── conventions/              # 팀 개발 규칙
└── runbook/                  # 운영·장애 대응 how-to
```

문서 종류는 다음처럼 구분합니다.

| 종류 | 질문 | 위치 |
|---|---|---|
| Reference | 현재 API와 시스템이 무엇인가? | `docs/api/` |
| How-to | 특정 작업을 어떻게 하는가? | `docs/runbook/` |
| Feature spec | 무엇을 만들고 언제 완료인가? | `docs/features/` |
| Explanation | 왜 이렇게 설계했는가? | `docs/adr/` |

## 작성 규칙

- Markdown 파일 하나에는 하나의 기능, API 묶음, 결정 또는 절차만 기록합니다.
- 파일명은 영문 소문자와 하이픈을 기본으로 합니다. 번호가 필요한 ADR은 `0001-title.md` 형식을 사용합니다.
- 문서 첫 부분에 상태, 담당 범위, 마지막 갱신일, 관련 문서 링크를 둡니다.
- 모호한 표현 대신 결정된 값, 상태 코드, 필드명, 완료 조건을 적습니다.
- 코드와 문서가 달라지면 같은 PR에서 함께 수정합니다.
- 구현되지 않은 내용은 `상태: draft` 또는 `상태: proposed`로 표시합니다. 완료된 것처럼 적지 않습니다.
- 과거 결정은 삭제하지 않고 ADR 상태를 `superseded`로 변경한 뒤 새 ADR로 대체합니다.
- 긴 대화 로그나 회의록 전체를 복사하지 않고, 결정·근거·할 일을 요약합니다.

## 변경 절차

1. 기능 작업을 시작할 때 `docs/features/`에 작업 명세를 만든다.
2. API 계약이 바뀌면 구현 전에 `docs/api/` 명세를 갱신한다.
3. 구조·보안·데이터 모델처럼 되돌리기 어려운 결정은 `docs/adr/`에 ADR을 작성한다.
4. 구현과 테스트를 진행한다.
5. PR 전에 문서의 상태와 완료 조건을 갱신하고 코드·문서 불일치가 없는지 확인한다.

문서만 추가하는 작업도 일반 코드 변경과 같은 브랜치·커밋·PR 규칙을 따릅니다.

## 참고 기준

- [OpenAPI Specification](https://spec.openapis.org/oas/v3.0.0.html): API path, operation, request, response 구조
- [MADR](https://adr.github.io/madr/): Markdown 기반 ADR의 context, options, outcome, consequences 구조
- [Diátaxis](https://diataxis.fr/): reference, how-to, feature spec, explanation 문서의 목적 구분
