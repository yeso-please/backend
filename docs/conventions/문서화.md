# 문서화

구현에 필요한 최종 정보는 저장소 Markdown에 남긴다. 한 문서에는 한 가지 목적만 둔다.

## 문서 위치

```text
docs/
├── README.md          유일한 입구(읽기 순서)
├── product.md         제품 정책과 결정 기록 — 무엇을 왜 만드는가
├── api/               API 계약과 구현 체크리스트 — 무엇을 호출하는가
├── design/            계산 방식(추천·코스 배치) — 어떻게 계산하는가
├── adr/               되돌리기 어려운 기술 결정
├── conventions/       팀 규칙(코드·모듈·테스트·협업·문서·설정)
├── runbooks/          운영 절차(RDS·이관)
└── archive/           대체된 이력. 구현 근거로 쓰지 않는다
```

작업 단위(목표·범위·완료 기준)는 문서가 아니라 **GitHub 이슈**에 둔다. 이슈는 명세를 복사하지 않고 `docs/api/`의 절을 링크한다.

## 작성 규칙

- 모호한 표현 대신 결정된 값, 상태 코드, 필드명, 완료 조건을 적는다.
- 코드와 문서가 달라지면 같은 PR에서 함께 고친다.
- 구현되지 않은 계약은 `draft`, 구현 상태는 명세 배지(`✅`·`🔧`·`⬜`)로 표시한다. 완료된 것처럼 적지 않는다.
- 제품 정책을 바꾸면 [product.md](../product.md) 본문을 고치고 결정 기록에 한 줄 남긴다. 기술 결정은 [ADR](../adr/README.md)로 남긴다.
- 대체된 문서는 지우거나 `docs/archive/`로 옮긴다. 본문에 폐기된 내용을 남겨 두지 않는다.
- 긴 대화 로그나 회의록 전체를 복사하지 않고 결정·근거·할 일만 요약한다.

## 작업 흐름

1. 이슈에서 담당 API 절과 완료 기준을 확인한다.
2. 계약을 바꿔야 하면 구현 전에 `docs/api/`를 먼저 고친다.
3. 되돌리기 어려운 기술 결정이면 ADR을 쓴다.
4. 구현과 테스트를 한다.
5. PR에서 체크리스트 배지를 갱신하고 `Closes #이슈`를 쓴다.

## 이슈 작성

목표(한두 줄), 담당 API 표(명세 링크), 완료 기준 체크리스트, 선행 이슈·결정 필요 항목, 참고 링크를 둔다. 완료 기준은 상태 코드·저장 데이터·권한·테스트처럼 검증 가능한 문장으로 쓴다. 범위 밖 아이디어는 별도 이슈로 나눈다.

## API 명세 작성

REST API 명세는 OpenAPI의 구조를 사람이 읽기 쉬운 Markdown으로 유지합니다. 각 endpoint에는 path, HTTP method, 인증, 입력, 성공 응답, 알려진 실패 응답을 반드시 기록합니다.

구현보다 먼저 명세를 작성하고, Controller·DTO·예외 처리와 내용이 일치하도록 유지합니다. Swagger가 추가되면 이 문서를 대체하지 않고, 사람이 검토하는 API 계약과 자동 생성 문서의 기준을 맞춥니다.

### 파일과 이름

```text
docs/api/
├── README.md       개요·호출 주체·공통 오류·구현 체크리스트
├── auth.md         § 1  auth
├── profile.md      § 2  profile
├── trip.md         § 3~6 trip (context·invite·course·diary)
└── attraction.md   § 7  attraction
```

HTTP를 노출하는 모듈(BC)마다 파일 하나를 둡니다. endpoint는 Controller가 속한 모듈의 파일에 두고, 파일 안의 절은 `presentation` 하위 패키지를 따릅니다. 이 폴더는 구현 여부와 관계없는 MVP 목표 계약이며, 구현 진척은 README의 체크리스트로 표시합니다.

### endpoint 템플릿

절 머리에는 계약 상태(`agreed`·`draft`), 공통 응답 타입, 오류 코드 표를 둡니다. endpoint는 다음 모양입니다.

````markdown
### 5-3. 일정 편집

> `호출: 참여자` · `⬜ 미구현`

```
PATCH /api/courses/{tripId}/schedule
```

**Request Body**

```json
{"version": 3, "operations": [{"op": "REMOVE", "itemId": "a-105"}]}
```

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `version` | `number` | 예 | 직전에 받은 값 |

**Response `200 OK`** — `Course`

| 오류 | HTTP | code |
|---|---:|---|
| 버전 불일치 | 409 | `TRIP_VERSION_CONFLICT` |

**Side effects** — 무엇을 만들고 바꾸는지.

**구현과의 차이** — `🔧 변경 필요`일 때만.
````

- 배지: `호출: …` · `✅ 구현|🔧 변경 필요|⬜ 미구현`. 호출 표기의 뜻은 `docs/api/README.md`에 있습니다. 계약은 구현 작업(GitHub 이슈) 단위와 독립적으로 쓰며 본문에 이슈 번호를 적지 않습니다. 예외로 파일 끝 "결정 필요" 표에는 막히는 이슈를 적습니다.
- 구현 상태를 바꾸면 README 체크리스트의 같은 행도 함께 바꿉니다.
- 미결 항목은 본문에 흩어 두지 않고 파일 끝 "결정 필요" 표에 모읍니다.

### 반드시 기록할 항목

- 실제 호출 path와 HTTP method
- 인증·인가 요구사항
- Path, query, header, body의 필드와 필수 여부
- 성공 상태 코드와 응답 예시
- 예상 가능한 400·401·403·404·409 응답
- 페이지네이션, 정렬, 필터, 기본값
- 데이터 변경이나 외부 API 호출 같은 side effect
- 멱등성, 재시도, 동시성 제약
- 관련 GitHub 이슈와 ADR

### 변경 규칙

기존 응답 필드 삭제·이름 변경, 필수 필드 추가, 상태 코드 변경은 호환성에 영향을 주는 변경입니다. PR 본문(필요하면 관련 이슈·ADR)에 영향 범위와 기존 클라이언트가 쓸 수 있는 전환 방법을 적습니다([계약 변경 절차](../api/README.md#계약-변경-절차)).

단순한 설명·오타 수정은 API 버전을 올리지 않아도 되지만, 계약이 바뀌면 문서와 테스트를 같은 PR에서 변경합니다.

## 에이전트 작업

에이전트는 [`docs/README.md`](../README.md)의 읽기 순서를 따른다. 문서와 코드가 다르면 추측으로 메우지 않고 차이를 작업 결과에 남긴다. 작업 결과에는 변경 사항, 실행한 검증 명령과 결과, 갱신한 문서, 미해결 사항을 적는다. 커밋·push는 사람이 요청할 때만 한다.
