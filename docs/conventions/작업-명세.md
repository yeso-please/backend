# 작업 명세

기능 개발은 Issue나 대화에서 바로 코드로 옮기지 않고 `docs/features/`에 실행 가능한 작업 명세를 남깁니다. 이 문서는 사람과 에이전트가 같은 목표·범위·완료 기준을 공유하기 위한 기준점입니다.

## 파일 이름

```text
docs/features/{domain}-{verb}.md
```

예시:

```text
docs/features/auth-social-login.md
docs/features/trip-create-plan.md
docs/features/attraction-search.md
```

## 템플릿

````markdown
# 여행 계획 생성

- 상태: draft | ready | in-progress | blocked | done
- 담당 범위: trip
- 작성일: 2026-09-17
- 갱신일: 2026-09-17
- 관련 이슈: #123
- 관련 API: [여행 API](../api/trip.md)

## 목표

사용자가 지역과 이동 수단을 선택해 여행 계획을 확정할 수 있다.

## 범위

### 포함

- 로그인 사용자의 여행 계획 생성
- 요청값 검증
- 생성 결과 반환

### 제외

- 여행 계획 수정
- 추천 코스 생성

## 사용자 흐름

1. 사용자가 인증된 상태로 생성 API를 호출한다.
2. 서버가 입력값과 리소스 존재 여부를 검증한다.
3. 서버가 계획을 생성하고 `201 Created`를 반환한다.

## 완료 기준

- [ ] 유효한 요청이 201을 반환한다.
- [ ] 잘못된 요청이 공통 에러 형식을 반환한다.
- [ ] 존재하지 않는 지역은 404를 반환한다.
- [ ] 인증되지 않은 요청은 401을 반환한다.
- [ ] 성공·실패 통합 테스트가 있다.
- [ ] API 문서가 구현과 일치한다.

## 구현 메모

## 결정과 미해결 사항

- 결정된 내용은 ADR 링크로 옮긴다.
- 미해결 사항은 담당자와 다음 행동을 적는다.

## 변경 이력

| 날짜 | 변경 | 이유 |
|---|---|---|
| 2026-09-17 | 초안 작성 | 작업 시작 |
````

## 완료 기준

완료 기준은 검증 가능한 문장으로 씁니다. “기능 구현 완료”처럼 판단이 필요한 표현 대신 상태 코드, 저장 데이터, 권한, 테스트 결과를 적습니다.

작업 중 범위가 바뀌면 명세를 먼저 갱신하고, PR 본문에 변경 이유를 적습니다. 범위 밖의 아이디어는 별도 Issue로 분리합니다.
