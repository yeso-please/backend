# 협업 규칙

브랜치·커밋, 이슈 라벨, CI 규칙이다. 작업은 GitHub 이슈(마일스톤 `MVP`, `추가 기능`)로 나누고 PR에 `Closes #이슈`를 쓴다.

## 브랜치와 커밋

### 브랜치

```text
main
  ↑
feat/fix/refactor/...  ← 작업 브랜치
```

모든 작업은 `main`에서 작업 브랜치를 만들고 PR로 반영합니다.

```text
feat/auth-social-login
feat/trip-create-plan
fix/auth-refresh-token
refactor/domain-package-structure
docs/backend-conventions
chore/spring-profile
```

설명은 영어 소문자와 하이픈을 사용합니다.

### 커밋

```text
{type}: {한국어 설명}
```

허용 타입은 `feat`, `fix`, `refactor`, `test`, `perf`, `docs`, `chore`, `infra`입니다.

```text
feat: 여행 계획 생성 API 추가
docs: 백엔드 컨벤션 문서 추가
chore: 로컬 프로파일 설정 추가
```

하나의 커밋은 하나의 논리적 변경만 포함합니다. PR 제목은 변경 목적을 한 줄로 설명하고, 본문에는 개요·작업 내용·관련 이슈·리뷰 포인트를 적습니다.

## 이슈 라벨 기준

### 작업 종류 라벨

종류는 주된 목적 하나를 선택한다. 기능 구현에 테스트·문서가 포함된다고 종류를 여러 개 붙이지 않는다.

| 라벨 | 기준 | 색상 |
|---|---|---|
| feat | 새 기능·기능 확장 | 2DA44E |
| bug | 잘못된 동작 수정 | D73A4A |
| infra | 빌드·CI·배포·실행 환경 | 8B5CF6 |
| docs | 문서 자체의 작성·정리 | 0075CA |
| refactor | 동작을 유지하는 코드 구조 개선 | FFA500 |
| chore | 그 외 유지보수·진행 현황 관리 | 6E7781 |

### 영역 라벨

실제로 변경하거나 책임을 다루는 영역 1~2개를 선택한다. 단순히 호출하는 모든 영역을 붙이지 않는다.

| 라벨 | 담당 영역 | 색상 |
|---|---|---|
| area: auth | 계정·로그인·토큰 인증 | C5DEF5 |
| area: profile | 온보딩·여행 성향·취향 임베딩 | C5DEF5 |
| area: attraction | 지역·관광지·식당·공식 코스·콘텐츠 품질 | C5DEF5 |
| area: trip | 여행·참여자·일정 생성/편집·초대/공유 | C5DEF5 |
| area: shared | 공통 오류·인증 주체·웹 설정 | C5DEF5 |

platform은 작업 분류이며 별도 Java 패키지를 뜻하지 않는다.

전체 구조 문서·진행 현황처럼 전역 작업에는 모든 영역을 나열하지 않아도 된다. 종류·영역 이름을 같은 의미의 동의어로 중복 생성하지 않는다.

### 역할 분리

- 담당자: Assignee
- 진행 상태: Projects의 Todo / In progress / In review / Done
- 범위: Milestone (`MVP`, `추가 기능`)
- 우선순위: 필요할 때 Projects의 Priority
- 진행 불가: 필요한 경우 `blocked` (D73A4A)와 원인·선행 이슈 링크. 단순히 나중에 할 작업이라는 이유로 붙이지 않는다.

제목은 기존 `{type}: 한국어 설명`을 유지한다. 버그 수정 제목의 fix와 이슈 라벨 bug는 역할에 맞게 사용한다. 영역 라벨은 [API 명세](../api/README.md)의 파일(모듈) 구분을 따른다.

라벨과 마일스톤은 저장소에 만들어져 있다. GitHub 기본 라벨(`enhancement`, `documentation` 등)은 위 이름으로 정리할 대상이다.

## 병렬 작업 충돌 줄이기

- **Flyway 버전 번호**: PR을 열기 전에 `main`으로 rebase하고 비어 있는 다음 `V` 번호를 쓴다. 두 PR의 번호가 겹치면 나중에 병합하는 PR이 번호를 바꾼다. 이미 병합된 migration은 절대 고치지 않는다.
- **ErrorCode**: MVP API의 오류 코드는 `ErrorCode`에 미리 등록돼 있다. 구현자는 그것을 쓰고, 새 코드가 필요하면 자기 모듈 블록(`// ---- {module} ----`)의 끝에만 추가한다.
- **구현 체크리스트**: [`docs/api/README.md`](../api/README.md)의 체크리스트는 PR마다 자기가 구현한 행만 바꾼다.

## CI

**CI가 실패(빨간색)한 PR은 병합하지 않는다.** 브랜치 보호로 강제하지 않으므로 병합하는 사람이 직접 확인한다.

모든 PR은 다음 검사를 통과해야 합니다.

```text
./gradlew compileJava
./gradlew test
```

포매터를 도입한 뒤에는 로컬에서 수정 명령을 실행하고 CI에서는 검사만 실행합니다.

```text
./gradlew spotlessApply
./gradlew spotlessCheck
```

CI는 컴파일 실패와 테스트 실패를 머지 차단 조건으로 사용합니다. PR 본문에는 실제 실행한 검증 명령과 결과를 적습니다.

GitHub Actions(`.github/workflows/ci.yml`)가 PR과 `main` push마다 Java 21로 `./gradlew compileJava test`를 실행합니다. 통합 테스트는 Testcontainers PostgreSQL 17에 Flyway migration을 모두 적용한 뒤 돕니다. 운영 DB 변경은 CI가 하지 않습니다.
