# 디렉터리 구조와 의존성

## 디렉터리 구조

```text
com.yeso.backend/
├── auth/
│   ├── domain/
│   ├── application/
│   ├── infrastructure/
│   └── presentation/
├── trip/
│   ├── domain/
│   ├── application/
│   │   ├── context/      TripService
│   │   ├── invite/
│   │   ├── course/
│   │   └── diary/        (추가 기능)
│   ├── infrastructure/
│   └── presentation/
│       ├── context/      TripController, 요청·응답 DTO
│       ├── invite/
│       ├── course/
│       └── diary/        (추가 기능)
├── attraction/
│   ├── domain/
│   ├── application/
│   │   ├── region/
│   │   └── ingestion/
│   ├── infrastructure/
│   └── presentation/
│       └── region/
├── profile/
│   ├── domain/
│   ├── application/
│   │   ├── onboarding/
│   │   └── friend/       FriendQueryService(다른 모듈용 친구 조회)
│   ├── infrastructure/
│   └── presentation/
│       ├── onboarding/
│       └── friend/
└── shared/
    ├── config/           AuthCookieProperties, CorsProperties, Clock 빈 등
    ├── exception/
    ├── persistence/
    ├── security/
    ├── token/            OpaqueTokenGenerator, TokenAudience, 토큰 예외
    └── web/
```

- `trip`은 위 구조 그대로다. 여행 context 코드(`TripController`·`TripService`와 DTO)는 `presentation/context`·`application/context`에 있다. 여행기(`diary`)는 추가 기능 이슈가 만든다.
- `profile`은 `application`·`presentation` 아래를 `onboarding/`·`friend/`로 나눈다. 다른 모듈이 친구 여부를 확인할 때는 `profile.application.friend.FriendQueryService`를 쓴다.
- `attraction/application/region`·`ingestion`과 `presentation/region`은 담당 이슈(#40 등)가 채운다.
- `shared/token`은 여러 모듈이 쓰는 불투명 토큰 발급기와 용도 구분(`TokenAudience`: 접두사 `iv_` 초대, `sl_` 공유 링크, `ss_` 공유 세션, `fl_` 친구 초대 링크), `TokenAudienceMismatchException`·`InvalidExpiresInDaysException`을 둔다. trip 초대·공유 링크와 profile 친구 초대 링크가 함께 쓴다.

## 계층별 책임

| 계층 | 책임 |
|---|---|
| `domain` | 엔티티, 값 객체, Enum, 도메인 규칙 |
| `application` | 유스케이스 조율, 권한 검사, 트랜잭션 |
| `infrastructure` | Repository, 외부 API·인프라 연동 |
| `presentation` | Controller, Request/Response DTO |
| `shared` | 공통 오류, 인증 주체, 감사 시각, 시계(`Clock`), 불투명 토큰, 웹·쿠키 설정 |

클래스는 소유 도메인의 패키지에 둡니다. 최상위에 공용 `domain` 패키지를 만들지 않습니다.

## 기능 하위 패키지

여러 유스케이스를 다루는 모듈은 `application`과 `presentation` 아래를 기능별로 나눕니다. `domain`과 `infrastructure`는 모듈 안에서 공유합니다.

HTTP를 노출하지 않는 기능은 `presentation` 하위 패키지를 만들지 않습니다. 계층을 채우기 위한 빈 서비스나 단순 위임 클래스는 만들지 않습니다.

## 의존성 규칙

- `domain`은 `application`, `infrastructure`, `presentation`을 import하지 않습니다.
- `shared`는 특정 도메인을 import하지 않습니다.
- 모듈 간 기능 호출은 `application`의 공개 계약을 사용합니다. 다른 모듈의 Repository를 직접 호출하거나 소유 엔티티를 직접 수정하지 않습니다.
- **현재 허용하는 예외(MVP):** 아래 네 가지뿐이다. 새 코드는 이 예외를 넓히지 않고, MVP 이후 각 모듈 `application`의 공개 조회 계약으로 옮긴다. `ArchitectureTest`는 infrastructure 예외(`UserRepository`, `RegionRepository`)만 허용하도록 강제한다.
  1. `auth.infrastructure.UserRepository`와 `User` 엔티티 — trip·profile이 회원 조회에 직접 쓴다.
  2. `User.latestOnboardingSubmissionId` 포인터 — `profile`이 갱신한다.
  3. `attraction.infrastructure.RegionRepository`와 `attraction.domain.Region` 엔티티 — profile(온보딩 지역 검증)·trip(여행의 지역 참조)이 읽기로 쓴다.
  4. `trip.infrastructure.TripPlanRepository.lockUser` — 날짜 중복 검사를 직렬화하려고 trip이 회원 행(`User`)을 잠근다.
- 새 모듈 간 호출(예: 코스 생성기)은 `presentation` DTO가 아니라 `application` 계층의 타입으로 주고받습니다.
- 도메인 간 엔티티 참조는 필요한 경우에만 사용하며, 모듈과 기능 하위 패키지 사이에 순환 의존성을 만들지 않습니다.
- API URL이나 작업 담당자가 아니라 데이터 소유권과 기능의 책임을 기준으로 코드를 배치합니다.
