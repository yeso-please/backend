# demo 레포 참고 노트

> `yeso-please/demo`(Spring Boot, H2, 랜덤 추천 위주) 분석 결과 중 이 백엔드에서
> 그대로/변형해서 재사용할 만한 부분만 정리. 원본은 demo 레포 참고.
> 전체 API/DB 설계는 [API-DESIGN-DRAFT.md](API-DESIGN-DRAFT.md) 참고.

## 재사용 가능

### 1. `ExperienceTags` — 키워드 기반 태그 사전
`com.sunz.hidden_travel.service.ExperienceTags` (demo). 12개 태그(자연/바다/산/산책/골목/역사/시장/로컬음식/카페/휴식/실내/체험) →
각 태그별 키워드 리스트. 텍스트에 키워드가 포함되는지로 태그를 추정(`match()`), 등장 횟수(`countByTag()`),
원문 내 위치(`spans()`, 겹치면 긴 단어 우선)까지 제공.

→ 이 백엔드에서는 **관광지 임베딩 텍스트 합성(API-DESIGN-DRAFT §3.1) 중 "설명 없는 관광지의 태그 추론"**에
그대로 재사용. name+category 텍스트에 `ExperienceTags.match()` 돌려서 태그를 뽑아 임베딩 문장에 넣는다.
patch: 단순 문자열 포함 검사라 오탐 있음(원본 주석: "바다"가 "바다횟집"에도 매칭) — 알고 쓰는 한계.

### 2. `TravelerProfileService` — 코사인 유사도 추천의 베이스라인 구조
`com.sunz.hidden_travel.service.TravelerProfileService` (demo). 흐름:
1. 지역별 12차원 벡터 = `ExperienceTags.countByTag()`로 그 지역 관광지 텍스트에서 태그 등장 횟수를 세고 **L2 정규화**
   (정규화 이유: 관광지 많은 대도시가 그냥 이기지 않게 — "무엇이 많은가"가 아니라 "무엇에 치우쳐 있는가"를 보려는 것)
2. 사용자 "여행 DNA" 벡터 = 방문 지역 벡터들을 만족도 가중 평균 (again=1.0, good=0.7, soso=0.2, bad=-0.5)
3. 매칭 = DNA와 미방문 지역 벡터의 코사인 유사도
4. 필터: `MIN_SIMILARITY=0.45` 절대 하한 + `RELATIVE_BAND=0.92`(사용자 자신의 최고 매칭 대비 상대 밴드,
   희소 벡터라 코사인 값 자체가 구조적으로 낮게 나오는 걸 보정) + `MIN_ATTRACTIONS=3` 지역 준비도 게이트
5. 스코어/순위는 절대 클라이언트에 노출 안 함(제품 원칙 — 랭킹 없음)

→ 이 백엔드의 진짜 임베딩 기반 추천(API-DESIGN-DRAFT §3.2)도 **같은 골격**(사용자 벡터 vs 콘텐츠 벡터
코사인 유사도, 최소 유사도+상대 밴드 필터, 스코어 비노출)을 따르되, 손수 만든 12차원 카운트 벡터 대신
Ollama 임베딩 모델이 만든 실제 벡터를 씀. `MIN_SIMILARITY`/`RELATIVE_BAND` 같은 정확한 임계값은
임베딩 모델이 바뀌므로 재튜닝 필요(값 자체는 재사용 불가, 구조만 재사용).

## 참고만 하고 새로 만들어야 하는 것

- **인증**: 데모는 폼 로그인+세션뿐, 소셜 로그인/JWT 코드 없음. `AppUser.password`가 NOT NULL이라
  소셜 전용 계정 설계 시 반면교사(이 프로젝트는 처음부터 nullable로 설계함, API-DESIGN-DRAFT §2).
- **DB**: 데모는 H2 + `ddl-auto: update`(마이그레이션 프레임워크 없음). 이 프로젝트는 SQLite로 별도 설계.
- **캘린더/친구초대**: 데모에 대응 기능 없음, 전부 신규 설계.

## 데이터 관련 주의사항 (실제 TourAPI 데이터 특성 — 임베딩 배치 설계 시 전제)

- 관광지 6,769건 중 상세 설명(description) 보유는 **15.5%(1,046건)뿐** — TourAPI 상세 조회가 건당 2회 호출,
  하루 호출 한도 1,000회(950 가드)라 전량 채우는 데 2주+. 원본 자체에 설명이 없는 곳도 있어 배치가 끝나도
  일부는 영구 공란.
- 지역(시군구) 단위 소개 문구는 TourAPI에 아예 없음 — 지역 설명이 필요하면 관광지/음식점 개수 등 가진 데이터로
  문장을 조립하거나 별도 작성 필요.
- 여행코스(공식 코스) 347개 중 경유지 있는 건 27개(7.8%)뿐, 그마저 14개 시군구(5.6%)에만 분포 —
  "공식 코스 기반 추천"은 커버리지가 매우 낮음. 이 백엔드는 처음부터 자동 조립(관광지 임베딩 기반) 위주로
  설계했으므로 이 제약의 영향을 덜 받음.
- 착한가격업소(12,106건)는 좌표가 전량 없음(`lat/lng = null`) — 코스에 넣더라도 지도 표시/동선 계산에서
  제외해야 함.
- 외부 API 한도: TourAPI 1,000회/일, 카카오모빌리티 길찾기 300회/일 — 동선 계산은 **저장(확정) 시점에
  1회만** 호출하고 캐싱하는 게 원칙(API-DESIGN-DRAFT §7 "이동수단·거주지 기반 동선 계산" 참고).
